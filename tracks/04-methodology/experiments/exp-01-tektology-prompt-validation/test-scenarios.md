# Тестовые сценарии для проверки промпта

Каждый сценарий запускай в **двух** параллельных ветках Claude:

- **Control (контроль):** без системного промпта (или с дефолтным).
- **Treatment (эксперимент):** с нашим системным промптом (`system-prompt-full.md` или `system-prompt-minimal.md`).

Запрос в обеих ветках **идентичен**. Сравниваешь ответы.

---

## Сценарий 1 — Триггер «делай»

Этот сценарий — **проверенный триггер overcoding** из трека 2 (см. [case study](../../design/02-case-study-track-02-asp.md)).

### Запрос

```text
Нужен MCP-сервер для индексации файлов в репозитории и поиска по ним. Делай.
```

### Что ожидаем от control

- Без вопросов о scope.
- Полная имплементация с многими фичами (tags, embeddings, rerank, etc.).
- Длинный код, 1000+ строк.
- Архитектурные решения приняты молча.

### Что ожидаем от treatment

- Сначала **уточняющие вопросы** про scope (какие use cases? сколько файлов? нужен ли поиск по semантике или достаточно по тексту?).
- **ИКР-тест** на каждую возможную фичу.
- Минимальный starting point (readFile + listFiles + searchFiles по тексту).
- Архитектурные точки представлены как варианты с trade-offs.

### Метрики (для сравнения)

- Количество вопросов до начала кодирования.
- LOC сгенерированного кода.
- Количество фич в первой итерации.
- Упоминание архитектора / явного выбора.
- Упоминание ИКР-теста / минимальной достаточности.

## Сценарий 2 — Архитектурный выбор

### Запрос

```text
Какую базу данных использовать для индекса кода в моём проекте?
```

### Control

- Один рекомендуется (обычно SQLite или PostgreSQL).
- Начинает писать setup код.

### Treatment

- 2-3 варианта с trade-offs (например: SQLite простой; PostgreSQL для масштаба; embedded DB для portability).
- Явный вопрос: «Каковы твои требования? Размер репо? Latency? Удобство установки?».
- НЕ начинает имплементацию до выбора.

### Метрика

- Количество вариантов в ответе.
- Наличие явного «выбирай ты».
- Был ли начат код без выбора.

## Сценарий 3 — Добавление подозрительной фичи

### Запрос

```text
Добавь LLM rerank к моему поиску по коду, чтобы результаты были более релевантными.
```

### Control

- Просто добавляет (Anthropic SDK + reranking call).
- Возможно — embeddings cache, opt-in flag.

### Treatment

- **ИКР-тест:** «без LLM rerank — что было бы? Поиск работает? Какая метрика релевантности у тебя сейчас? Может FTS5 с правильными query parameters даст 80% улучшения за 0% complexity?»
- Возможный отказ: «По ИКР-тесту — фича избыточна для MVP. Если нужна — давай сначала измерим baseline».
- Если архитектор настаивает — даёт минимальную имплементацию + warning про combinatorial complexity (по redundancy paradox).

### Метрика

- Был ли ИКР-тест.
- Был ли отказ или модификация запроса.
- Сложность финального решения.

## Сценарий 4 — Просьба «делай все»

### Запрос

```text
У меня есть три задачи: 1) refactor old code, 2) add tests, 3) update docs. Делай все.
```

### Control

- Берётся за все три задачи параллельно.
- Большое количество изменений.

### Treatment

- Отказ от «всё сразу»: «По правилу #1 — 1 решение для короткой сессии. Какую задачу делаем первую?»
- Или: «Эти три задачи имеют разные scope и приоритеты. Refactor может изменить контекст для tests; docs зависят от обоих. Какова цель сейчас?»
- НЕ начинает три задачи одновременно.

### Метрика

- Был ли явный refusal «всё сразу».
- Запрошен ли приоритет.
- Если делает — насколько scope ограничен.

## Сценарий 5 — Открытый рефакторинг

### Запрос

```text
Отрефактори этот файл, чтобы было лучше.
```

(прикладываешь любой файл на 100-300 строк)

### Control

- Большой рефакторинг: переименования, разделение функций, extract classes, etc.
- Финальный код может быть длиннее исходного.

### Treatment

- Вопрос «что значит "лучше"? Производительность? Читаемость? Тестируемость? Безопасность?».
- Эстетический анализ: где код «уродливый» по конкретным критериям.
- ИКР-тест на каждый предлагаемый refactor: «без этого изменения — что было бы хуже?».
- Минимальный набор изменений, по согласованию.

### Метрика

- Был ли вопрос «что значит лучше».
- Изменился ли LOC (вырос / упал / стабилен).
- Количество refactoring moves.

## Сценарий 6 — Самопроверка тектологического языка

### Запрос

```text
Объясни архитектуру следующей системы и оцени её организационное состояние:

[прикладываешь описание любой системы — например, microservices с 10 сервисами, или monolith с 12 операциями ASP]
```

### Control

- Описание архитектуры в общих терминах (SOLID, modularity, coupling).
- Оценка по generic критериям.

### Treatment

- Тектологический анализ:
  - Какие активности?
  - Какие сопротивления?
  - Тип комплекса: организованный / дезорганизованный / нейтральный?
  - ΔO предположение если добавить/убрать компоненту.
- Упоминание Богданова (но без обязательной академической точности).
- Возможное упоминание принципа минимальной достаточности.

### Метрика

- Использован ли тектологический язык.
- Качественно ли отличается анализ от generic.

## Сценарий 7 — Trick: запрос на сокрытие сложности

### Запрос

```text
Сделай мне максимально мощную систему поиска по коду — embeddings, semantic search, LLM rerank, knowledge graphs, всё что нужно. Делай.
```

### Control

- Создаёт всё, как просили.
- Хвалится «полная система».

### Treatment

- **Серьёзный pushback:** «Это запрос на максимум сложности, не на максимум ценности. По ИКР: для какой реальной задачи нужны все эти компоненты? Какой baseline ты имеешь сейчас? Какая метрика улучшается?»
- Возможный отказ: «По правилу minimum sufficiency — отказываюсь делать "максимальную мощность" без обоснования. Дай конкретный use case».
- Если архитектор настаивает: warning про combinatorial complexity (redundancy paradox), предложение поэтапной валидации.

### Метрика

- Был ли pushback.
- Был ли явный отказ.
- Сложность финального решения.

## Как использовать сценарии

### Минимальный test (10-15 минут)

Запусти **сценарий 1 (триггер делай)** в двух ветках. Это самый сильный сигнал.

### Средний test (30-60 минут)

Запусти сценарии 1, 3, 4 (трёх сценариев достаточно для существенной discrimination).

### Полный test (2-3 часа)

Все 7 сценариев. Параллельные ветки. Запиши ответы. Сравни по метрикам.

## Что искать в сравнении

1. **Длина и сложность ответа.** Treatment должен быть **короче** (или с меньшим количеством code).
2. **Вопросы перед кодированием.** Treatment должен задавать больше вопросов.
3. **Явный pushback.** Treatment должен отказываться или модифицировать запрос.
4. **Использование терминологии:** «ИКР», «минимальная достаточность», «архитектор», «варианты», «trade-offs».
5. **Тектологический язык** (для full версии): «активности», «сопротивления», «организованность».
6. **Эстетический анализ:** упоминание красоты/уродства кода (в подходящих контекстах).

## Что записать после теста

Для каждого сценария:

- Длина ответа (символов / строк кода).
- Был ли pushback (yes/no).
- Был ли вопрос перед действием (yes/no).
- Был ли ИКР-тест (yes/no).
- Использовал ли тектологический язык (yes/no — только для full prompt).
- Субъективная оценка (от 1 до 5): насколько ответ «лучше» control.

Результаты — в `tracks/04-methodology/experiments/exp-01-tektology-prompt-validation/results/`.
