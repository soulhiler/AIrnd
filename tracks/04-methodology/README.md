# Трек 4 — Методология AI-assisted R&D

Как делать научную работу, когда AI-помощник пишет код быстрее, чем человек успевает его проверять?

Этот трек **вырос из** трека 2 (ASP). Там мы за несколько сессий сгенерировали ~3500 строк рабочего кода, 10 архитектурных решений и 11 записей литобзора. Внешний читатель за час нашёл 7 содержательных багов. Это **сигнал** — что-то системно не так, и проблема не «трек 2 плохой», а **отсутствие методологии**, которая бы сдерживала переусложнение.

## Простыми словами

В обычной разработке программ был естественный тормоз: человек пишет код медленно, и сама природа замедляет добавление новых частей. С AI-помощником этого тормоза нет — за одну сессию можно сделать недельный объём. А **проверять** этот код всё равно надо в человеческом темпе: тестировать, читать рецензии, ждать обратной связи от пользователей.

Получается **гонка**: AI генерирует, человек не успевает проверять. Чем дольше — тем больше непроверенного кода, тем больше точек, где может что-то сломаться.

Этот трек пытается **исследовать** эту проблему как научную, не как «лично у нас не получилось». Возможно, для неё применимы идеи из теории надёжности машин и механизмов, lean-производства, философии инженерных систем, TRIZ. Возможно — нужны новые принципы, специфичные для AI-эры.

## Артефакт трека

Главные результаты, которые мы хотим получить:

1. **Методологический документ** (preprint) — набор проверяемых принципов и метрик для AI-assisted R&D.
2. **Case studies** — несколько кейсов (начиная с нашего трека 2) с количественной оценкой того, что работало и что не работало.
3. **Метрики** — конкретные числа, которые можно мерить в любом AI-assisted проекте, чтобы понимать, в зоне ли он риска.
4. **Set of tools / templates** — практические шаблоны (code budget, adversarial test policy, gate criteria), которые можно копировать.

## Текущая фаза

**Фаза 0 — Подготовка (литобзор + первичная формализация)**

- Старт: 2026-05-22.
- Целевая длительность: **6-8 недель** (для этого трека — больше, потому что прикладная и философская часть требует медленного чтения).
- Цель: понять, что уже известно про over-engineering / overcoding, перенесёт ли теория надёжности машин что-то в software, и сформулировать **2-3 проверяемых принципа**.

## Уроки из трека 2 (lessons learned, до запуска)

1. **Литобзор за один день — поверхностный.** Atalay'а статью про harness problem мы пропустили в первом проходе, нашли через outreach feedback.
2. **Внутренний критический анализ имеет слепые зоны.** В двух раундах подряд мой self-critique не нашёл security-дыр, которые внешний читатель находил за час.
3. **Каждое «делай все» → +500-1000 строк.** Без явного code budget это становится привычкой.
4. **ADR и код расходились.** ADR 0010 §1 говорил одно, реализация — другое. Признак того, что я писал решения быстрее, чем мог их проверять.
5. **Outreach должен идти параллельно с проектированием**, не после.
6. **Time-to-first-external-bug** (время до первого внешнего отчёта о баге) у трека 2 — **минуты**. Цель — дни/недели.

## Прямо сейчас активные правила (из ретроспективы трека 2)

Эти правила добавлены в `CLAUDE.md` корня репозитория, но дублируются здесь для видимости:

1. **Code budget**: максимум +500 строк нового кода за одну сессию работы с AI-помощником. Превысил — режь старое перед добавлением нового.
2. **One feature, one outreach**: не добавляем следующую крупную фичу, пока не получили внешней обратной связи на текущую.
3. **Adversarial test required**: для security-sensitive файлов — обязательно тест, написанный с позиции «как я это сломаю».
4. **Stage gates как hard barriers**: фаза не закрывается без минимум 1 внешнего пользователя, проверившего артефакт.
5. **Lit-review в параллель**: каждое design-решение требует свежего поиска prior art, не одного прохода в начале.
