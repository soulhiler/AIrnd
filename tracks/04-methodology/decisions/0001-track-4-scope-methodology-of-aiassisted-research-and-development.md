# 0001. Track 4 scope: методология AI-assisted R&D

- **Дата:** 2026-05-23
- **Статус:** accepted
- **Связанные ADR:** —
- **Исходный сигнал:** трек 2 (ASP) сгенерировал ~3500 строк, 10 ADR, 11 lit-review за несколько сессий. Внешний читатель за час нашёл 7 содержательных багов. Самокритика автора пропустила те же баги дважды.

## Простыми словами

Открываем новый трек о том, **как делать R&D с AI-помощником, не уходя в перепроизводство кода**. Это не трек про ASP, не про конкретный продукт — это **мета-трек** о методике работы. Опыт трека 2 становится первым кейсом для анализа.

Главная гипотеза: проблема **системная**, не «у нас лично не получилось». Природа AI-помощника такова, что код производится быстрее, чем человек способен его проверять. Этот разрыв скоростей создаёт переусложнение. Возможно, для борьбы с этим переносятся идеи из теории надёжности машин и механизмов (минимальная достаточность), lean-производства, TRIZ.

## Context

После двух раундов внешнего аудита трека 2 (Alex, май 2026) стало ясно:

1. **Скорости разработки и проверки разошлись.** За несколько сессий с AI-помощником сгенерировано больше кода, чем один человек способен проверить. Каждое внешнее ревью находит баги быстрее, чем мы успеваем их закрывать.
2. **Самокритика автора не работает как защита.** В двух раундах подряд внутренний critical analysis пропустил security-дыры, которые внешний читатель находил за минуты. Это структурное — автор не может adversarially тестировать свой код в реальном времени.
3. **Существующие R&D методологии (lean startup, agile, scrum) не покрывают этот случай.** Они разработаны для команд людей с естественным темпом производства. AI-помощник этот темп ломает.
4. **Это значимая universal-проблема.** Скоро (если не уже) большинство R&D-программ будет использовать AI-помощников. Methodology, которая бы сдерживала overcoding, нужна не только нам.

Трек 2 в этом смысле становится **первичными данными** для исследования: подробно задокументированный кейс программы, которая ушла в overcoding, с трейсом решений, диффами, временными метками, внешними аудитами. Не лабораторный, не идеальный, но **реальный**.

Параллельно мы видим в существующих дисциплинах кандидатов на перенос:

- **Теория надёжности машин и механизмов** (особенно советская инженерная школа): принцип минимальной достаточности — компонент имеет ровно столько усложнения, сколько нужно для функции.
- **TRIZ** (Альтшуллер): законы развития технических систем, S-curve, переусложнение как сигнал достижения потолка.
- **Lean manufacturing / Toyota Production System**: borderline waste, kaizen, validated learning.
- **Закон Брукса**: добавление людей замедляет проект. Аналог: добавление кода тоже.
- **Закон Конвея + Tesler's law**: сложность не уничтожается, она перераспределяется.

Открытый вопрос: какие из этих принципов переносятся прямо, какие требуют адаптации, и есть ли что-то **новое**, специфичное для AI-эры, что нужно сформулировать с нуля.

## Decision

**Открываем трек 4 «Методология AI-assisted R&D» как параллельный трек R&D-программы.**

Конкретно:

1. **Scope.** Трек исследует, как сдерживать переусложнение и переразработку в R&D с AI-помощником. Артефакты: методологический документ (preprint), 2-3 case studies, набор измеримых метрик, практические шаблоны (code budget, gate criteria, adversarial testing policy).

2. **Сейчас становится главным треком программы.** Трек 2 (ASP) ставится на паузу — мы не добавляем туда новый код, пока не получили второго и третьего внешнего отзыва. Это **прямое применение** правила «one feature, one outreach», которое мы сейчас и пытаемся формализовать.

3. **Темп — медленный, осознанно.** Целевая длительность Фазы 0: **6-8 недель** (vs 3-4 недели по ТЗ для типичного трека). Литобзор должен быть глубоким, не однодневным. Каждое design-решение требует свежего поиска prior art.

4. **Первичные данные — наш собственный трек 2.** Подробная case study с метриками: сколько кода, за какое время, сколько багов нашёл внешний аудит, какой был half-life каждой фичи. Это **уникальные** данные, которые сложно собрать в другом контексте.

5. **5 правил вступают в силу прямо сейчас** (зафиксированы в `CLAUDE.md`):
   - Code budget: ≤500 строк нового кода за сессию.
   - One feature, one outreach.
   - Adversarial test required для security-sensitive файлов.
   - Stage gates как hard barriers.
   - Lit-review в параллель, не одним проходом.

6. **Эти правила сами по себе — гипотезы**, не аксиомы. Эмпирически валидируем их в этом треке.

## Consequences

### Positive

- **Реальный шанс получить публикуемый методологический результат.** Тема актуальна, primary data есть, gap в существующей литературе вероятно.
- **Применение к нашим собственным трекам.** Трек 1 (когда активируется), будущие треки получают готовую методику.
- **Универсальная польза.** R&D-сообщество в эпоху AI-помощников нуждается в этом.
- **Метатрек дисциплинирует основной поток.** Сам факт того, что мы анализируем наш процесс, замедляет нас — и это хорошо.

### Negative

- **Расфокус.** Трек 2 ставится на паузу — потенциально теряем momentum в outreach. Mitigation: эта пауза — часть исследования трека 4, она и есть применение правила «one feature, one outreach».
- **Риск академической абстракции.** Мета-исследования склонны производить красивые принципы без эмпирической базы. Mitigation: трек 2 как primary data, метрики количественные.
- **Самоссылочность.** Трек, который изучает overcoding, может сам уйти в overcoding методологии. Mitigation: применяем правила трека 4 к самому треку 4. Code budget, one feature one outreach — на этот трек тоже.
- **Темп замедляется.** Меньше «делай все» сессий, больше пауз на чтение. Психологически менее удовлетворительно. Это **намеренная стоимость**.

## Alternatives considered

### Alternative A: Не открывать новый трек, добавить уроки как раздел в трек 2

Просто извлечь уроки из ретроспективы трека 2 и применять их в треке 1, когда тот стартует. Никакого нового трека, никакого литобзора.

Отклонено: уроки без обоснования через литературу — это просто «личные правила», а не методология. Преимущество отдельного трека — обязательство сделать научное обоснование, а не интуитивный набор.

### Alternative B: Сделать только design doc, без полноценного трека

Один документ `docs/methodology.md` без литобзора, без ADR, без структуры трека.

Отклонено: легковесный документ быстро устаревает или забывается. Полный трек с phases / gates / preprint даёт **обязательство** довести до публикации.

### Alternative C: Подождать второго или третьего кейса (трек 1, трек 3)

Не начинать методологическое исследование на одном кейсе (трек 2). Дождаться 2-3 завершённых треков, иметь больше data.

Отклонено: ждать может занять месяцы или годы. Трек 2 как single rich case study — достаточная основа для **первых гипотез**. Дополнительные кейсы добавятся естественно с течением треков и валидируют/опровергнут принципы.

### Alternative D: Сделать external research collaboration

Найти академика, который изучает software engineering productivity, и сотрудничать. Не делать самостоятельно.

Отклонено сейчас: pre-engagement без артефакта = слабая позиция. Сначала делаем v0.1 design doc внутри, потом можно искать сотрудничество для эмпирической части.
