# Аршинский, Аршинский, Бахвалов 2019 — Принципы необходимости и достаточности в систематизации ПО

## Простыми словами

Это **самая важная prior-art работа** для нашего трека 4 — но она оказалась **другой**, чем мы предполагали по абстракту.

Авторы (трое из Иркутска — отец, сын и коллега) ставят вопрос **классификации ПО**: как разложить программы по полочкам так, чтобы один и тот же objet не попадал в две полки одновременно. Их вывод: существующие классификации (системное / прикладное / инструментальное) **неявно опираются на «принцип достаточности»** — то есть на то, **что программа МОЖЕТ делать**. Это размывает границы: Photoshop одновременно «профессиональное» и «досуговое» ПО.

Они предлагают **«принцип необходимости»** — классификация по тому, **что программа ОБЯЗАНА делать**, без чего нельзя обойтись.

И это **другая «достаточность»**, чем у нас. У нас «минимальная достаточность» = «ровно столько фич, сколько надо для функции, не больше». У них «достаточность» = «возможности программы». Слова те же, смысл разный.

**Что Аршинские дают нам:**

1. **Формальный язык** — нотация `¬A → ¬B` для «A необходим для B», три типа необходимости (экзистенциальная / функциональная / целевая). Мы можем **заимствовать** эту нотацию.
2. **Три аспекта существования объекта** (существует / функционирует / достигает целей) — это **тонкая структура**, которую можно встроить в наш ИКР-тест.
3. **Понятия «ценность» vs «полезность»** — A ценен для B если без A нельзя; A полезен для B если A достаточно (но возможно есть и другие).

**Чего Аршинские НЕ дают нам:**

1. **Не дают принципа дизайна.** Их principle of necessity — про классификацию **существующего** ПО, а не про то, **что строить**. Наш вопрос («как не уйти в overcoding при создании») у них не ставится.
2. **Не цитируют ТРИЗ, Брукса, теорию надёжности.** Это значит — наша триангуляция остаётся **нашей оригинальной**. Аршинские дают **формальный аппарат**, мы — **принцип**.
3. **Не учитывают AI-эпоху** (статья 2019, до Copilot/Claude). Естественно.
4. **Не дают количественных метрик** для границы «достаточно vs избыточно».

**Итог:** prior art есть, но **не покрывает** наш центральный thesis. Покрывает **формальную базу**, на которой можно построить более строгую формулировку нашей минимальной достаточности.

## TL;DR

Аршинские с Бахваловым формализуют **принцип необходимости** как основу классификации ПО. Они говорят: традиционные классификации (системное / прикладное / инструментальное) неявно опираются на принцип достаточности (что программа **может** делать), но это размывает границы — Photoshop одновременно профессиональный и досуговой инструмент.

Принцип необходимости (что программа **должна** делать) даёт более чёткое разделение. Вводятся три типа необходимости (экзистенциальная / функциональная / целевая) и формальная нотация `¬A → ¬B`. На основе принципа строится иерархия слоёв ПО S0 (железо) → S1 (драйверы) → S2 (ОС) → S3 (компиляторы) → S4 (компилированное прикладное + интерпретаторы) → S5 (интерпретируемое прикладное) → S6 (пользователь).

Это **формализм для классификации**, а **не методология для дизайна**.

## Key claims (с указанием раздела/страницы)

- **Claim 1 — Существующие классификации ПО опираются на принцип достаточности неявно.** (Стр. 18, Введение.) Цитата: «Создается впечатление, что многие авторы исходят из интуитивных представлений о классификации программных объектов... Порой нарушается базовый принцип классификации: один элемент – один класс, принцип полноты разбиения». Это **критика** существующего state of the art.

- **Claim 2 — Три аспекта существования объекта** (стр. 19, §1):
  1. **Базовый (экзистенциальный)** — объект существует.
  2. **Функциональный** — объект (существуя) функционирует, хотя бы частично работоспособен.
  3. **Целевой** — объект (функционируя) достигает поставленных перед ним целей.

  И: **«между аспектами существования объектов также существует отношение необходимости: 1 необходим для 2; 2 необходим для 3»**. Это **тонкая иерархия** — существование первично, функция вторична, цель третична.

- **Claim 3 — Формальное определение необходимости** (стр. 19, Определение 1):
  > «Объект A необходим для объекта B, если существование, функционирование или достижение цели объектом B невозможно в полной мере вне объекта A, когда утрата объекта A либо части его функциональности означает хотя бы частичный ущерб для B.»

  Нотация: `¬A → ¬B`. Подвиды: `→e` (экзистенциально), `→f` (функционально), `→g` (целево).

- **Claim 4 — Формальное определение достаточности** (стр. 19-20, Определение 2):
  > «Объект A достаточен для объекта B, если существование, функционирование или достижение цели объектом A означает также существования, функционирование или достижение цели (хотя бы частично) объектом B.»

  Нотация: `A → B`.

- **Claim 5 — Ценность ≠ полезность.** (Стр. 20.) Если в системе есть две равнозначных программы `A1` и `A2`, каждая отдельно не имеет **ценности** (можно удалить любую, оставив другую), но каждая обладает **полезностью**. И наоборот, если `A1` и `A2` необходимы только **совместно** — ни одна по отдельности не полезна.

- **Claim 6 — Иерархия слоёв ПО.** (Стр. 20-22, §2.) Применяя принцип необходимости с правилом «если O нужны слои i1…ik, то O принадлежит слою ik+1»:
  - **S0** = аппаратные средства (АС).
  - **S1** = драйверы, firmware (управление отдельными узлами АС).
  - **S2** = ОС (управление АС как системой). Цитата: «отсутствие ОС не влияет на работоспособность отдельных АС в ИВС».
  - **S3** = ИПО (инструментальное ПО — компиляторы).
  - **S4** = ППО компилированное + ИПОИ (интерпретаторы).
  - **S5** = ППО интерпретированное (скрипты, макросы).
  - **S6** = пользователь.

- **Claim 7 — Классификация по необходимости устраняет размытость классов.** (Стр. 22.) Цитата: «Если опираться на принцип достаточности, одна и та же программа может попасть более чем в одну группу… Классификация по необходимости выглядит более последовательной».

- **Claim 8 — Сетевое ПО** имеет другую структуру слоёв (стр. 23, §3): локальные ЭВМ как S0, сетевое оборудование S1, и т.д. до S6 = ПО над браузерами, S7 = пользователь.

## Methodology

**Формально-логический подход.** Не эмпирический, не экспериментальный. Авторы строят систему определений (1 и 2) и применяют их к существующим типам ПО. Результат — иерархия слоёв.

**Силы:**
- Чёткие определения с формальной нотацией.
- Применимость продемонстрирована конкретными примерами (Photoshop, СУБД, виртуальные машины, сетевое ПО).
- Прозрачная критика существующих подходов через нарушение «один элемент — один класс».

**Слабости:**
- Нет empirical validation (никто не проверял, действительно ли классификация по необходимости даёт меньше пересечений на больших выборках реального ПО).
- Нет квантификации (как **измерить** степень необходимости?).
- Только 9 источников в библиографии, все русские, все — текстбуки/учебные материалы. **Нет связи с международной литературой** по software classification.
- Не учитывает AI-эпоху (статья 2019).

## Gap (для нашего трека)

### Что Аршинские **дают** нам (полезно для трека 4)

1. **Формальный язык** для разговора о принципе. Нотация `¬A → ¬B` точнее, чем наш качественный язык «без фичи: что было бы?». Можно записать формально для каждой фичи: «удаление фичи X означает ¬F (функция не выполнена)?». Это **подмножество ИКР-теста**, но более строгое.

2. **Три аспекта существования** (existential / functional / goal). Это **прямое расширение** нашего ИКР-теста. Сейчас в шаблоне ADR один вопрос «без фичи: что было бы?». По Аршинским — три уровня:
   - Без фичи: разрушится ли существование системы?
   - Без фичи: разрушится ли функция?
   - Без фичи: разрушится ли достижение цели?

   Фича может быть нужна для **одного** аспекта (например, для функции) и не нужна для другого (например, для существования). Это **тонкий instrument**.

3. **Понятия «ценность» vs «полезность»** даёт нам словарь для разговора об избыточных фичах. Если в проекте две равнозначных фичи — каждая «полезна», но ни одна не «ценна» (одна из них **избыточна**). Это **критерий** для отлова дубликатов.

4. **Иерархия слоёв** даёт идею для классификации фич внутри проекта. В треке 2 (ASP): какие операции принадлежат S1 (без них **никакого** ASP нет — readFile), какие — S4 (без них качество хуже — retrieve)? Удалять можно только из верхних слоёв.

### Что Аршинские **не покрывают** (наш contribution)

1. **Принцип дизайна, а не классификации.** Они классифицируют существующее ПО. Мы — **что строить**. Это разные вопросы. Наш central thesis (минимальная достаточность для дизайна) — НЕ их thesis.

2. **Связь с другими источниками.** Они не цитируют ТРИЗ, Брукса, теорию надёжности. Наша триангуляция — оригинальная. Расширение до 4 источников (с Аршинскими) делает наш каркас ещё сильнее, но они в этой триангуляции — не вершина, а **дополнительная база**.

3. **AI-эпоха.** 2019 — до Copilot, до GPT-4, до Claude. Все наши вопросы про AI-assisted разработку у них не ставятся. Это **наша уникальная** территория.

4. **Количественная мера.** Их подход качественный — yes/no для каждой необходимости. У нас в треке 4 — попытка вывести количественные правила (decisions per session, lit-review counts по классу). Это **наше дополнение**.

### Сценарий взаимодействия — Аршинские как **инструмент**, мы как **методология**

Они дают **формальный язык**: 3 аспекта × нотация → классификация артефакта. Мы берём язык и применяем к **новому контексту**: AI-assisted разработка, где артефакт ещё **не существует** и решается «строить или нет».

В нашем переводе:
- Их «¬A → ¬B (existential)» = наш вопрос «без фичи: продукт исчезнет?».
- Их «¬A → ¬B (functional)» = «без фичи: функция не работает?».
- Их «¬A → ¬B (goal)» = «без фичи: пользователь не получит ценность?».

Если хотя бы один из ¬-ответов = «нет» (без фичи всё ОК) — фича избыточна по этому аспекту. Если **все три** = «нет» — фичу не делаем точно.

Это **формализация ИКР-теста** через язык Аршинских.

## Личные заметки

### Что зацепило

- **«Принцип необходимости» как явное противопоставление «принципу достаточности»** — это **разделение слов**, которое мы у себя не делали. У нас «достаточность» (в «минимальной достаточности») имела двойной смысл: с одной стороны «функция выполнена», с другой «не больше, чем надо». Аршинские разделяют чётко. Стоит **переименовать** наш центральный thesis: либо «принцип необходимости + минимальности», либо явно сказать, что наша «достаточность» = их «необходимость» + «минимум».

- **Три аспекта (existential / functional / goal) с иерархией между ними** — это **очень полезно**. Особенно факт, что **аспекты сами связаны отношением необходимости**: существование необходимо для функции, функция необходима для цели. Это даёт нам **порядок проверки**: сначала «существование», потом «функция», потом «цель». Если фича не нужна для существования — есть шанс что не нужна и для функции. Это **дерево решений**, не плоский чеклист.

- **Ценность ≠ полезность** — концептуально мощно. Это объясняет, почему мы в треке 2 имели много «полезного» (каждая операция что-то делает), но **мало ценного** (без половины операций система продолжала бы работать). Конкретно: 12 операций ASP, из которых ~5 необходимы (S1-S2 в их слоях), ~7 полезны но не необходимы. **Это в точности соответствует нашей оценке 60% overcoding** — без независимого подтверждения.

### С чем не согласен / что бы сделал иначе

- **«Достаточность = возможности» как у них** — мне кажется этот терминологический выбор немного неудачным. В обычном русском «достаточность» имеет коннотацию «достаточно для какой-то цели», а у Аршинских это «способность сделать что-то». Это **переопределение**, на которое надо обращать внимание читателя.

- **Иерархия слоёв S0-S6** — она работает для **изолированных** машин, но у Аршинских не очень развит вопрос **многокомпонентных** распределённых систем. В §3 они упоминают сетевое ПО, но это **отдельная** иерархия, а не унифицированный подход.

- **Они не рассматривают вопрос «как **измерить** необходимость**». В каждом примере у них — «отсутствие ОС не влияет на работу драйверов, поэтому S2 после S1». Но это **качественное** утверждение. В сложных системах **количество** взаимной необходимости может быть важным (например, 10% функций ОС используются драйверами vs 90%). Этот вопрос у них не разработан.

### Идеи для трека 4

1. **Расширить ИКР-секцию в шаблоне ADR** до трёх вопросов по Аршинским (вместо одного):
   - Без фичи: разрушится ли существование системы? (existential)
   - Без фичи: разрушится ли функция? (functional)
   - Без фичи: разрушится ли достижение цели? (goal)

   Если ВСЕ ТРИ ответа «нет» — фичу не делаем точно. Если хотя бы один ответ «да» — пишем дальше с указанием **какого** аспекта это касается.

2. **Заимствовать нотацию `¬A → ¬B`** для формального записи зависимостей в проектах:
   - Например: `¬asp_readFile → ¬ASP` (existential — без readFile ASP не существует).
   - Например: `¬asp_retrieve → ¬ASP_quality` (только goal — без retrieve качество хуже, но протокол работает).

   Это даёт **точный язык** для ADR, который мы сейчас не имеем.

3. **«Ценность vs полезность» как чеклист дубликатов.** Перед добавлением фичи спросить: «Есть ли в проекте фича, делающая то же самое или близкое?». Если есть — обе фичи **полезны**, но **ценности** теряют. Это **критерий отказа** от добавления.

4. **Слои ПО как метрика overcoding.** Классифицировать каждую фичу по слою (existence / function / goal). Если фич в слое «goal» больше, чем в «existence + function» — это **сигнал** про over-engineering на верхнем уровне.

5. **Расширить триангуляцию** до 4 источников в design doc 03. Аршинские дают **формальный аппарат**, не **principle**. Это **дополняющая** работа, не **конкурирующая**.
