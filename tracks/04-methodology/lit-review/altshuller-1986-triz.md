# Альтшуллер 1969-2006 — ТРИЗ (теория решения изобретательских задач)

## Простыми словами

Генрих Альтшуллер 50 лет изучал патенты — миллионы изобретений — и нашёл, что **технические системы развиваются по предсказуемым законам**. Не каждое изобретение уникально — большинство решают типовые проблемы типовыми приёмами. Альтшуллер их каталогизировал и сформулировал законы развития.

Главная идея, релевантная нашей: **системы стремятся стать «идеальными» — то есть выполнять функцию, не существуя.** Велосипед без рамы (карбон-трубки), мотор без двигателя (электрический), счётчик без механизма (электронный). Это **прямая формулировка** принципа минимальной достаточности через цель.

И ещё — **S-кривая**: любая система проходит фазы (медленный рост → быстрый рост → потолок → стагнация или замена). Это **диагностический инструмент** для понимания «где мы сейчас» и стоит ли усложнять дальше или пора **упрощать**.

## TL;DR

ТРИЗ (Теория решения изобретательских задач) — методология, разработанная Альтшуллером на базе анализа ~40 000 патентов. Главные концепции:

- **ИКР (идеальный конечный результат):** функция выполнена, а компонента нет. Это **формальный** способ задать минимальную достаточность.
- **40 приёмов изобретательства:** каталог типовых приёмов (сегментация, обратное действие, динамизация, и т.д.) для разрешения противоречий.
- **Законы развития технических систем:** статика (целостность, проводимость, согласование), кинематика (повышение идеальности, S-кривая, неравномерность развития частей), динамика (переход на микроуровень, увеличение управляемости).
- **Противоречие:** техническое (улучшение A ухудшает B) и физическое (требуется свойство X и не-X одновременно) — фундаментальные конструкции для постановки задачи.
- **S-кривая:** все системы проходят 4 фазы — медленный рост (детство), быстрый рост (зрелость), потолок (стабилизация), упадок (замена). На потолке усложнение даёт почти 0 эффекта.

## Key claims

- **Claim 1 — ИКР (идеальный конечный результат).** «Максимум нового эффекта при минимуме затрат на реализацию». Все системы развиваются в направлении увеличения идеальности. **Прямая формализация** принципа минимальной достаточности из теории надёжности.
- **Claim 2 — Закон S-кривой.** Каждая техническая система проходит детство → зрелость → потолок → упадок. На потолке любое усложнение даёт diminishing returns и часто **ухудшает** систему (бритва с 7 лезвиями).
- **Claim 3 — Закон неравномерности развития частей.** Разные компоненты эволюционируют с разной скоростью. Дисбаланс рождает **узкое место** — компонент-«тормоз», который определяет скорость всей системы.
- **Claim 4 — Закон перехода на микроуровень.** Развитые системы заменяют макро-компоненты на микро (механика → электрика → электроника → программа). На пределе функция выполняется «полем» — без материального носителя.
- **Claim 5 — Противоречие как корень задачи.** Изобретательская задача всегда содержит противоречие: «нужно X, но это ухудшает Y». Решение через ТРИЗ — найти приём, разрешающий противоречие без trade-off (а не компромисс).
- **Claim 6 — Алгоритм АРИЗ.** Последовательность шагов от формулировки задачи до решения. Не «как родить идею», а **где искать идею системно**.

## Methodology

Альтшуллер использовал **патентный анализ** как primary data — изучил ~40 000 патентов (по своей оценке) за 50 лет. Это **наблюдательное исследование** на гигантском датасете, не контролируемые эксперименты.

Сила: настоящий patentary corpus — реальные инженерные решения, не теоретические модели.
Слабость: систематические biases выборки (что попадает в патент vs народное творчество), нет статистической методологии в современном смысле (validation, p-values).

В современной ТРИЗ-сообществе — расширения через cause-effect chains, function-oriented search, S-curve metrics. Есть critiques (TRIZ как «soft science», воспроизводимость спорная).

## Gap (для нашего трека)

### Что переносится прямо

1. **ИКР как формальный критерий минимальной достаточности.** Для каждой фичи в проекте можно спросить: «А что было бы, если бы этой фичи **не было**, а её функция как-то выполнялась?». Если ответ «всё было бы так же» — фича **избыточна**. Это **практический test**, который применим к каждому ADR.
2. **S-кривая для диагностики трека.** На какой фазе наш трек 2 (ASP)? Сейчас он на **потолке зрелости** — добавление фич даёт diminishing returns (например, hierarchical tags + LLM rerank — каждая фича решает всё меньше). По ТРИЗ это **сигнал**: пора упрощать, не добавлять.
3. **Противоречия как явная формулировка проблемы.** «Хочу больше функций, но меньше багов» — это **техническое противоречие**. ТРИЗ предлагает разрешать через приёмы (сегментация, vacuum cleaner principle, asymmetric design), не через компромисс.
4. **Закон неравномерности развития частей.** В треке 2 явно: операции (12) развиты, тестирование (43 теста) отстаёт, документация (1500 строк спеки) опережает имплементацию — все компоненты разной зрелости. По ТРИЗ — нужно подтягивать **узкое место** (тестирование), а не добавлять operations.

### Что НЕ переносится прямо

1. **Patent-derived корпус.** Software не патентуется типично; lessons learned распределены по open-source repos, blog posts, conference talks. Метод сбора другой.
2. **«Микроуровень» для software.** В технике переход на микроуровень означает «делаем меньше / используем поля». В software — «выкидываем код / используем uniform abstractions». Аналогия есть, но **не identical**.
3. **40 приёмов изобретательства.** Они конкретны (сегментация, "матрёшка", "наоборот", и т.д.) — заточены под механику. В software некоторые работают (декомпозиция = сегментация), некоторые странно (предварительная антидействие?).
4. **Алгоритмическая мощь АРИЗ.** В современной AI-эре, где LLM сам генерирует варианты — формализованный многошаговый АРИЗ может быть избыточен (AI уже делает мозговой штурм).

### Где наш трек делает вклад

- **«ИКР для overcoding»:** для каждой добавленной фичи в AI-assisted проекте — обязательная проверка «можно ли убрать эту фичу так, чтобы её функция выполнялась чем-то существующим?». Это можно встроить в ADR процесс трека 4 как обязательный пункт.
- **«S-кривая трека»:** диагностика фазы трека по объективным метрикам (количество новых operations за неделю, % refactor vs add). Когда добавления стабилизируются — мы на потолке, надо упрощать.
- **«Противоречие AI-era»:** «AI генерирует много, человек проверяет мало» — это **физическое противоречие** в ТРИЗ-смысле (нужна скорость генерации и скорость валидации одновременно). ТРИЗ предлагает приёмы для физических противоречий: разделить в **пространстве** (разные роли), во **времени** (синхронизация), в **отношениях** (между генератором и валидатором). Это уже даёт нам наши правила #1, #2 трека 4.

## Open questions

- **Q1:** ИКР даёт **формальный** критерий минимальной достаточности. Можно ли его встроить как обязательную секцию в ADR template (например, «ИКР: что было бы, если этой фичи не было?»)?
- **Q2:** S-кривая — есть ли software-специфичная метрика, по которой мы можем определить фазу проекта? Кандидаты: tests-per-feature ratio, refactor-vs-add ratio, count новых operations per session.
- **Q3:** TRIZ имеет критиков (воспроизводимость, надёжность 40 приёмов). Насколько мы можем доверять его выводам в нашем контексте?
- **Q4:** Закон перехода на микроуровень — в software означает что? Уход в DSL? Уход в декларативные подходы? Уход в self-modifying code? Не сформулировано.

## Related work cited

- **Брукс** (наш lit-review #1) — Brooks's «conceptual integrity» = ТРИЗ-овое «целостность системы» (закон статики).
- **Теория надёжности машин** (наш lit-review #2) — минимальная достаточность = ИКР, но в разных языках.
- **Современные TRIZ-исследования:** Petrov, Mann — продолжают развивать ТРИЗ в инженерных контекстах. arxiv [«Accelerating Science TRIZ inventive methodology in illustrations»](https://arxiv.org/pdf/1608.00536) — современный обзор.
- **Lean / Toyota Production System** — поверхностно рифмуется через идеал «zero waste». Но Lean более процессный, ТРИЗ более продуктовый.

## Личные заметки

### Что зацепило

- **ИКР как formal test.** Это первое прямое формальное правило, которое можно встроить **в process** трека 4. Каждый ADR должен иметь секцию «ИКР: что было бы, если бы этой фичи **не было**?». Если ответа нет (или ответ «всё было бы так же») — фича избыточна.
- **S-кривая для нашего собственного трека 2.** Я думаю, мы на **потолке зрелости** ASP — последние добавления (LLM rerank, hierarchical tags) решают всё меньше реальных проблем. По ТРИЗ это сигнал упрощать, не наращивать. Это **совпадает** с правилом #2 трека 4 («один проект, один outreach между фичами»).
- **Противоречие в TRIZ-форме**: наш «AI generates fast, human validates slow» — это **физическое противоречие**. ТРИЗ говорит — разрешается, не через компромисс, а через **разделение** (в пространстве/времени/отношениях). Это даёт **теоретическую базу** для правила #2 (разделение во времени между генерацией и validation).

### С чем не согласен / что бы сделал иначе

- **40 приёмов слишком конкретны для software.** Альтшуллер заточил их под механику. Применять буквально — sub-optimal. Но **формат каталога** приёмов — perfect для нашего трека 4 (каталог methodological приёмов против overcoding).
- **АРИЗ алгоритм — слишком процедурный.** В AI-эре много шагов АРИЗ выполняется LLM «бесплатно» (генерация вариантов, противоречие → idea). Не нужно следовать строго.
- **«50 лет 40 000 патентов»** — методологически сомнительно (нет controlled studies). Но прикладная **полезность** доказана через десятилетия применения в инженерии. Это **art > science**, как и наш собственный трек 4.

### Идеи для трека 4

1. **ИКР-секция в ADR template:** добавить обязательный пункт «Без этой фичи: что было бы?». Это **сильнее** того, что у нас сейчас (просто Alternatives considered). Это прямо включает позицию «убрать фичу» как первый вариант.
2. **S-кривая как метрика трека.** Простая heuristic: «если последние 3 фичи решили реально меньше проблем, чем первые 3 — мы на потолке». Применимо без особых вычислений.
3. **Каталог приёмов разрешения противоречий «AI overcoding»:**
   - **Разделение во времени**: правило #2 (one feature, one outreach).
   - **Разделение в пространстве**: правило #6 (явный choice human vs AI generation).
   - **Разделение в отношениях**: AI = генератор, human = архитектор/валидатор (ADR 0002).
   - Это уже **частично существующая структура**, ТРИЗ её **усиливает** через теоретическую базу.

### Cross-references

- **Brooks** (#1): conceptual integrity ≈ TRIZ закон статики (целостность). Брукс — эссеистский подход, ТРИЗ — формальный.
- **Теория надёжности** (#2): минимальная достаточность = ИКР. Это **тот же** принцип, разные формулировки. Если оба источника независимо приходят к одному выводу — это **сильный сигнал** что принцип верный.
- **Case study трека 2:** S-кривая прямо применима. Первые 4 операции (readFile, listFiles, searchFiles, findByTag) решили 80% use cases. Последние 4 (impact, writeFile, applyPatch, retrieve) — 20%. По ТРИЗ это означает «зрелость → потолок», и наш трек был на этой фазе **уже** когда добавляли последние фичи.
- **ADR 0002 трека 4** (классы проектов): TRIZ S-кривая может быть **классификатором фазы**, не только класса. «На какой фазе S-кривой ваш проект?» — отдельный axis от «класс проекта».

## Итоги партии B (Brooks + теория надёжности + TRIZ)

Три работы дают **сходящиеся** ответы на наш центральный вопрос «переносится ли что-то в AI-эру?»:

| Источник | Ключевой принцип | Совпадение с другими |
|---|---|---|
| **Brooks** | Conceptual integrity через single architect; omit features for unity | = ТРИЗ закон целостности; теория надёжности SPF |
| **Теория надёжности** | Минимальная достаточность; series formula; redundancy paradox | = ТРИЗ ИКР; Brooks «omit features» |
| **TRIZ** | ИКР; S-кривая; противоречия → приёмы | = тео надёжности минимальная достаточность; Brooks через unity |

**Triangulation:** **три independent traditions** независимо пришли к **одному ключевому правилу — минимальная достаточность**:

- Брукс: omit features for conceptual integrity (эссеистское обоснование).
- Теория надёжности: минимум деталей = минимум failure modes (математическое).
- ТРИЗ: ИКР — функция выполнена, а компонента нет (формально-методологическое).

Это **сильный сигнал** для трека 4: принцип минимальной достаточности — **наша центральная гипотеза**. Не просто «один из вариантов», а **основной thesis**.

### Что три работы НЕ дают

- Все три писали про **человеческую** разработку. AI-эра меняет правила (особенно стоимость генерации). Мы должны **расширить** их в нашей работе.
- Все три — про **продукт/систему**. Process (как организовать работу) у них вторичен. Lean и Continuous Discovery (следующие в литобзоре) — оттуда возьмём process side.
