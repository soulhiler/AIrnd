## Update — пересмотр парадигмы (вечером того же дня)

Сроки в треке 4 пересмотрены. Старые цифры («6-8 недель на литобзор», «4 недели на дизайн») — это **переписанные нормы из ТЗ**, которое предполагает что человек делает всё сам. С AI как генератором bottleneck сдвинулся.

Зафиксировано в [ADR 0002 — Парадигма работы](../decisions/0002-human-as-architect-ai-as-generator-paradigm.md).

Главные изменения:

- **Сроки сжаты в 5-10× по календарю** (полный трек ~6-8 недель вместо ~6 месяцев). Не за счёт халтуры — за счёт того что человек **не пишет**, а **направляет и валидирует**.
- **Метрика «строки за сессию» заменена на «decisions per session ≤3»**. У AI «сессия» может быть 15 минут и 5000 строк — старая метрика теряет смысл.
- **Добавлено правило #6**: ADR пишется как **явный выбор** человека из вариантов AI, не как готовое решение. Это закрывает разрыв «AI пишет ADR + код одновременно, человек кликает делай», который породил ADR-vs-код inconsistency в треке 2.
- **Outreach из «в конце» в «между этапами»**. Не дожидаемся завершения фазы — после каждого крупного артефакта ≥1 внешний отзыв.

`CLAUDE.md` обновлён (6 правил вместо 5). Корневой README обновлён. README трека 4 обновлён (gate criteria переформулированы).

### Применение правила #6 прямо сейчас

В этой сессии user явно выбрал из 4 предложенных артефактов («ADR + README + CLAUDE.md + notebook»). AI представил список, человек сказал «делай» — это **не явный выбор**, это **подтверждение**. По новому правилу #6 — это **не accepted**, это **черновик**.

Полное accepted для этого ADR требует, чтобы пользователь явно **выбрал** между:
- A. Принимаем парадигму как описано в ADR 0002.
- B. Принимаем, но с правками (какими).
- C. Отклоняем, остаёмся в старой парадигме.

Сейчас ADR 0002 помечен `accepted`, но это **формальная разметка**. Если user не подтвердит явно — статус нужно откатить на `proposed`.

**Это первое мета-наблюдение**: применение правила #6 к самому правилу #6 = рекурсия. Хороший знак.

## Update 2 — вариативность по классам проектов (user feedback)

User выбрал **вариант B** на вопрос про парадигму: «принимаем, но с правками — ситуации могут быть разные». Это значит — жёсткие числа («2-5 дней», «≤3 решения») заменяю на **адаптивные пороги**, зависящие от **класса проекта**.

### Что добавилось

В ADR 0002 — две новые секции:

1. **Классы проектов** (§2 расширен):
   - Малый: POC, 1 идея, ≤300 LOC, без публичного релиза.
   - Средний: компонент, 300-1500 LOC, ограниченный outreach.
   - Большой: RFC + impl, 1500-5000 LOC, публичный outreach.
   - Multi-track: связка треков.

2. **Адаптивные пороги** (§3 расширен):
   - Decisions per session — функция длины сессии (≤1 если короткая, до ≤3 если длинная).
   - Stage gates — N зависит от класса (1/2/3+).
   - Lit-review — диапазон по классу (3-5 / 8-12 / 15-25).

3. **Режимы ослабления/усиления:**
   - Ослабить можно (с записью в notebook) для exploratory режима, малого класса, исчерпанного бюджета.
   - Усилить надо для security-sensitive файлов независимо от класса, для публичного релиза, после внешнего аудита.

### Что отражает классификация

Трек 2 (ASP) — это **большой класс** проекта (1500+ LOC спека + 3500+ LOC impl, публичный outreach). Но мы вели его **в малом темпе** — закрывали фазы за 1 день. Отсюда несоответствие: большой проект, малая дисциплина, → overcoding.

Если бы мы с самого начала классифицировали трек 2 как «большой» и применили соответствующие пороги (Lit-review 15-25 работ + явное обоснование, Stage gates ≥3 валидаций, и т.д.), темп был бы естественно ниже.

### Применение к этой сессии

Эта сессия в треке 4 (методология) — **средний класс**: мы пишем документы (не код), один наблюдатель / архитектор, ограниченный outreach. По новой схеме:

- Decisions per session: сессия ~60 мин, лимит ≤2 решения. Реально: 1 решение (вариант B с правками) + 1 уточнение (что значит «вариативно»). На границе.
- Lit-review: на этом этапе не делаем (другая стадия).
- Stage gates: эта сессия — внутри Phase 0, gate ещё не подходит.
