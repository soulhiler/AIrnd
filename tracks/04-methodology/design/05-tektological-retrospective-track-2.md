# 05 — Тектологическая ретроспектива трека 2 (ASP)

## Простыми словами

В треке 2 (Agent Server Protocol) мы за 10 дней приняли 10 ADR (архитектурных решений) и написали ~3500 строк кода. Александр (внешний аудитор) в Round 1 нашёл 5 багов в 5 разных разделах кода — почти 100% случаев. Мы интуитивно поняли что было overcoding (~60%), но **не могли формализовать**, что именно пошло не так.

Теперь у нас есть **тектологический язык** (по Богданову, [lit-review #6](../lit-review/bogdanov-tektology.md)). Применяем его ретроспективно к каждой из 10 ADR — смотрим: какие активности и сопротивления были, какой получился комплекс (организованный/дезорганизованный/нейтральный), и **почему именно** возникало overcoding.

**Цель документа:** доказать, что **тектологический фреймворк действительно работает** для диагностики overcoding на нашем собственном кейсе. Это **empirical валидация** (или фальсификация) [design/03](03-minimum-sufficiency-triangulation.md).

## Метод

Для каждой ADR трека 2 (10 штук) делаем тектологический анализ:

1. **Какие активности** были в системе на момент ADR? (Что генерировал AI? Что валидировал человек? Какой код уже был?)
2. **Какие сопротивления** были? (Что мешало добавлению фичи? Какие side effects?)
3. **Тип комплекса после ADR:** организованный (1+1>2), дезорганизованный (1+1<0), нейтральный (1+1=2)?
4. **Был ли overcoding-сигнал?** (Сейчас, в ретроспективе, очевидный?)
5. **Что бы предсказала тектология?** (Закон наименьших, закон Ле-Шателье, относительность организованности.)

### Нотация (по Богданову + Аршинским)

- `A` = активность (что-то добавляющее в систему).
- `R` = сопротивление (что-то противодействующее активности).
- `O` = организованность комплекса. Знак: `O > 0` орг., `O < 0` дезорг., `O ≈ 0` нейтр.
- `∂O` = изменение организованности после ADR.

## I. Анализ 10 ADR трека 2

### ADR 0001 — MCP extension vs new protocol

**Решение:** Делать новый протокол (ASP), не расширение MCP.

**Тектологический анализ:**

- **A:** добавление 1 новой активности — protocol design.
- **R:** существующий MCP как стандарт (сопротивление через legitimacy). Сопротивление человека-архитектора (понимание trade-offs).
- **Тип комплекса:** **организованный**, `O > 0`. Чёткое решение, ясный scope, понятная мотивация (5 fixes над GitNexus). Это **правильный** старт.
- **Overcoding-сигнал:** нет.
- **Тектология предсказала бы:** успех. Решение **минимально-достаточно** для задачи.

**Вердикт:** good ADR. ∂O = +1 (организация повысилась).

### ADR 0002 — Scope: open-source agents only

**Решение:** Поддерживать только open-source агентов (Aider, Continue, Cline, Codex CLI).

**Тектологический анализ:**

- **A:** ограничение scope (это активность сокращения, не добавления).
- **R:** возможный объём работ для каждого агента (если бы поддерживали все).
- **Тип комплекса:** **организованный**, `O > 0`. Ограничение scope — **тектологически правильное** действие (закон минимума).
- **Overcoding-сигнал:** нет.
- **Тектология предсказала бы:** успех. Ограничение scope = повышение организации.

**Вердикт:** good ADR. ∂O = +1.

### ADR 0003 — Cleanroom build, parity + 5 fixes

**Решение:** Реализовать ASP с нуля, паритет с GitNexus + 5 улучшений.

**Тектологический анализ:**

- **A:** добавление **большой** активности — целая reference implementation.
- **R:** время человека, сложность параллельной разработки, синхронизация с спецификацией.
- **Тип комплекса:** **на границе**, `O ≈ 0`. Решение **большое**, но обоснованное.
- **Overcoding-сигнал:** **первый сигнал**! «5 fixes» — это **дополнительные** активности к базовому паритету. Каждый «fix» — отдельная сложность.
- **Тектология предсказала бы:** при правильном выполнении — организация. При расширении scope (что и произошло) — дезорганизация.

**Вердикт:** medium ADR. Был риск. ∂O = 0 (на грани, зависит от исполнения).

### ADR 0004 — Hierarchical tag schema

**Решение:** Иерархические теги как фича ASP.

**Тектологический анализ:**

- **A:** добавление новой активности — tag system.
- **R:** дополнительная сложность schema, performance impact, документация.
- **Тип комплекса:** **дезорганизованный**, `O < 0`. Это **первый яркий случай** overcoding. Tag system добавлен **на основе гипотезы**, не на основе реальной потребности пользователя.
- **Overcoding-сигнал:** **сильный**! `findByTag` — одна из операций, которая по ИКР-анализу ([design/03 §VI](03-minimum-sufficiency-triangulation.md)) — **избыточна**.
- **Тектология предсказала бы:** дезорганизация через рассогласование скоростей. AI быстро сгенерировал tag system, человек не успел проверить, нужна ли она.

**Вердикт:** bad ADR. ∂O = -1 (организация снизилась).

### ADR 0005 — Outreach deferred

**Решение:** Отложить outreach (внешние отзывы пользователей) до Gate 0→1.

**Тектологический анализ:**

- **A:** ничего не добавляется (отложение).
- **R:** **отсутствие** внешнего сопротивления (которое могло бы скорректировать направление).
- **Тип комплекса:** **дезорганизованный**, `O < 0`. Это **системная ошибка**: убрали единственный источник внешнего сопротивления.
- **Overcoding-сигнал:** **критический**. Это **корень** последующих ADR 0006-0010 — все они принимались без внешнего сопротивления.
- **Тектология предсказала бы:** дезорганизация. По закону Ле-Шателье (применимому к организационным системам, Богданов): система без внешних сопротивлений теряет равновесие и уходит в крайности.

**Вердикт:** very bad ADR. ∂O = -2 (организация снизилась сильно, на много шагов вперёд).

**Это, возможно, самое тектологически-неудачное решение трека 2.** Если бы оutreach остался, ADR 0006-0010 могли бы быть другими.

### ADR 0006 — Language TypeScript

**Решение:** TypeScript для reference implementation.

**Тектологический анализ:**

- **A:** добавление активности (выбор языка, setup tooling).
- **R:** инерция (надо учиться, конфигурировать).
- **Тип комплекса:** **нейтральный**, `O ≈ 0`. Решение разумное, ничего особенного.
- **Overcoding-сигнал:** нет.
- **Тектология предсказала бы:** успех или нейтрально (всё зависит от компетенции).

**Вердикт:** ok ADR. ∂O = 0.

### ADR 0007 — Storage: SQLite + FTS5

**Решение:** Использовать SQLite с full-text search для индекса.

**Тектологический анализ:**

- **A:** добавление активности (индексация, FTS5 schema).
- **R:** дополнительная зависимость, конфигурация.
- **Тип комплекса:** **организованный**, `O > 0`. SQLite + FTS5 — **минимально-достаточный** выбор для поиска. Не over-engineered.
- **Overcoding-сигнал:** нет. Это **хороший** ADR.
- **Тектология предсказала бы:** успех. Простой инструмент для конкретной задачи = высокая организация.

**Вердикт:** good ADR. ∂O = +1.

### ADR 0008 — Parser strategy: tree-sitter WASM

**Решение:** tree-sitter WASM для парсинга 12 языков.

**Тектологический анализ:**

- **A:** добавление активности (parser system, 12 grammars).
- **R:** WASM compilation, ABI compatibility (web-tree-sitter pinned to 0.22 because 0.26 breaks).
- **Тип комплекса:** **на границе**, `O ≈ 0`. tree-sitter сам по себе хороший, но **12 языков** — это уже сильное расширение scope. Возможно, MVP должен был быть для 1-2 языков.
- **Overcoding-сигнал:** **средний**. 12 языков — это «делай всё», не «делай минимум».
- **Тектология предсказала бы:** на границе. Зависит от того, сколько языков реально используется.

**Вердикт:** mediocre ADR. ∂O = 0 (на грани, риск дезорганизации в будущем через wear-out зависимостей).

### ADR 0009 — LLM rerank

**Решение:** LLM rerank через MCP sampling для улучшения retrieval.

**Тектологический анализ:**

- **A:** добавление **значительной** активности — embeddings (@xenova/transformers) + LLM rerank (Anthropic SDK + MCP sampling).
- **R:** complexity (3 модели взаимодействия), dependencies, performance, opt-in flags (`ASP_RERANK_PROVIDER`).
- **Тип комплекса:** **дезорганизованный**, `O < 0`. Это **классический пример** overcoding. По ИКР-анализу ([design/03 §VI](03-minimum-sufficiency-triangulation.md)) — `asp_retrieve` с embeddings + LLM rerank **очень вероятно избыточна** для MVP.
- **Overcoding-сигнал:** **очень сильный**. Каждая компонента (embeddings, rerank, opt-in flag) — отдельная сложность. По теории надёжности (Claim 4 lit-review #2): redundancy paradox — много opt-in путей **снижают** надёжность через combinatorial complexity.
- **Тектология предсказала бы:** сильная дезорганизация. Active growth >> resistance, ничто не остановило.

**Вердикт:** very bad ADR. ∂O = -2.

### ADR 0010 — Read/write separation + default-off mutations

**Решение:** Разделить read и write операции, mutations выключены по умолчанию.

**Тектологический анализ:**

- **A:** добавление активности (split, env flag, security gates).
- **R:** сложность реализации, дополнительный код.
- **Тип комплекса:** **частично организованный**, `O ≈ +1`. Хорошая идея (security), но **запоздалая** — должна была быть в ADR 0001-0003, а не после того, как Alex нашёл security баги.
- **Overcoding-сигнал:** **умеренный** — само решение хорошее, но **тайминг плохой**. Это **компенсация** прошлых ошибок, а не превентивная мера.
- **Тектология предсказала бы:** улучшение организации, но **через большое сопротивление** (рефакторинг существующего кода).

**Вердикт:** good idea, bad timing. ∂O = +1 (после), но не помогает с тем, что уже сделано.

## II. Аггрегированная картина

### Таблица ∂O по ADR

| ADR | Решение | ∂O | Тектологическая оценка |
|---|---|---|---|
| 0001 | MCP vs new protocol | +1 | Организованный. Минимально-достаточный старт. |
| 0002 | Open-source scope | +1 | Организованный. Правильное ограничение. |
| 0003 | Cleanroom + 5 fixes | 0 | На границе. Первый сигнал overcoding. |
| **0004** | **Hierarchical tags** | **-1** | **Дезорганизованный. Tag system на основе гипотезы.** |
| **0005** | **Outreach deferred** | **-2** | **Дезорганизованный. Системная ошибка — убрали внешнее сопротивление.** |
| 0006 | TypeScript | 0 | Нейтральный. |
| 0007 | SQLite + FTS5 | +1 | Организованный. Простой инструмент. |
| 0008 | tree-sitter 12 langs | 0 | На границе. 12 языков — over-scope. |
| **0009** | **LLM rerank + embeddings** | **-2** | **Сильно дезорганизованный. Redundancy paradox.** |
| 0010 | Read/write separation | +1 | Хорошая идея, плохой тайминг. |
| **Σ** | | **-1** | **Общая дезорганизация по сумме ADR.** |

### Ключевые наблюдения

1. **Σ ∂O = -1.** Сумма всех ∂O отрицательная. Это значит, **в среднем за трек 2 организованность снизилась**. Это согласуется с эмпирической оценкой «60% overcoding» и с Round 1 audit (5 багов в 5 разделах).

2. **ADR 0005 (outreach deferred) — корень проблемы.** Это решение убрало единственный источник внешнего сопротивления. Без него ADR 0006-0010 принимались **в вакууме**. Если бы оutreach остался — ADR 0009 (LLM rerank) **вероятно** был бы отвергнут или сильно урезан.

3. **ADR 0004 (tags) и ADR 0009 (rerank) — главные источники overcoding.** Оба добавили активности без реального сопротивления (валидации). По ИКР-анализу — оба избыточны.

4. **Хорошие ADR (0001, 0002, 0007) имеют общую черту:** они **ограничивают** scope или выбирают **минимально-достаточный** инструмент. Это **прямое подтверждение** Богданова: организация = разумное ограничение.

5. **Плохие ADR (0004, 0005, 0009) имеют общую черту:** они **расширяют** scope без соответствующего роста сопротивлений. Это **прямое подтверждение** Богданова: дезорганизация = рассогласование активностей и сопротивлений.

## III. Что бы изменилось, если бы тектология применялась с самого начала

Гипотетический сценарий: правила трека 4 (CLAUDE.md правила 1-6) + тектологическая мера `O` **применялись** в треке 2.

### ADR 0005 (outreach deferred) — отклонён

По правилу #2 («one feature, one outreach») — нельзя откладывать outreach. По тектологии — нельзя удалять внешнее сопротивление. **Был бы отклонён.**

Следствие: ADR 0006-0010 принимались бы **с внешним сопротивлением**. ADR 0009 (LLM rerank) **вероятно** был бы урезан до базового без embeddings/rerank.

### ADR 0004 (hierarchical tags) — отложен

По ИКР-тесту: «без hierarchical tags — что было бы?». Ответ: ASP-сервер работает (e=да), функция (f) поиска работает через searchFiles, цель (g) пользователя достигается. **Все три аспекта нейтральны** → фичу **не делаем** на старте, можно добавить если эмпирически нужно.

### ADR 0009 (LLM rerank) — отклонён или сильно урезан

По ИКР-тесту: «без LLM rerank — что было бы?». Ответ: ASP-сервер работает (e=да), retrieve функция работает (f=да, просто хуже sorting), цель достигается (g=да, просто менее удобно). **Все три аспекта нейтральны** → отклоняем или делаем как опциональный feature без default.

### Сводный итоговый прогноз

Если бы тектология применялась:

- 10 ADR → ~5-7 ADR.
- 3500 LOC → ~1500-2000 LOC.
- 5 багов в audit Round 1 → возможно 1-2 (меньше surface).
- Время до first outreach → 2-3 раундов раньше.

Это **прямое подтверждение** оценки 60% overcoding из case-study трека 2.

## IV. Что тектология предсказала, чего мы не видели

Кроме ретроспективного объяснения, тектология даёт **прогнозные** утверждения, которые мы можем проверить:

### Прогноз 1: web-tree-sitter 0.22 = бомба замедленного действия

ADR 0008 (tree-sitter 12 langs) использовал web-tree-sitter pinned to 0.22 (потому что 0.26 breaks ABI). По теории надёжности (Claim wear-out, lit-review #2): зависимости **изнашиваются** через эволюцию external API. Это **скрытое сопротивление**, которое сейчас не активно, но проявится через 1-2 года.

**Эмпирическая проверка:** в течение года-двух — наблюдать, ломается ли установка `asp-ref` из-за tree-sitter compatibility. Если ломается — тектология (закон wear-out) подтверждается.

### Прогноз 2: env flags как combinatorial explosion

ADR 0009 (LLM rerank) и связанные добавили `ASP_RERANK_PROVIDER`, `ASP_ENABLE_EMBEDDINGS`, `ASP_SKIP_GITIGNORE`, `ASP_ENABLE_MUTATIONS`. По теории надёжности (Claim redundancy paradox): каждый flag добавляет combinatorial path для багов.

**Эмпирическая проверка:** в следующих audit раундах — какая доля багов связана с конкретными комбинациями flags? Если значительная — теория подтверждается.

### Прогноз 3: будущий ASP_v0.2 — дезорганизация при `>3` новых фичах

По правилу #1 трека 4: ≤3 решения за сессию. По тектологии: каждая новая фича = новая активность, требующая нового сопротивления (валидации). Если v0.2 добавит >3 фичей без соответствующего роста валидаций — дезорганизация.

**Эмпирическая проверка:** при работе над v0.2 (когда возобновим) — считать decisions per session, оценивать ΔO.

## V. Выводы

### Главные

1. **Тектологический фреймворк действительно работает** для диагностики overcoding на нашем кейсе.
2. **Σ ∂O трека 2 ≈ -1** — общая дезорганизация. Это формальное (количественное) подтверждение интуитивной оценки «60% overcoding».
3. **ADR 0005 (outreach deferred) — корень всех зол.** Это **главный урок**: никогда не удалять внешнее сопротивление.
4. **ADR 0004 и 0009 — главные overcoding events.** Tag system и LLM rerank — обе фичи на основе гипотез, без проверки.

### Для трека 4

1. **Правило #2 (one feature, one outreach) — критически важное.** Тектологически подтверждено: без внешнего сопротивления система уходит в крайности.
2. **Метрика ΔO работает.** Можно считать ∂O для каждого ADR ретроспективно. Для проактивного применения — нужно операционализировать дальше.
3. **Тектология даёт прогнозы.** Не только описывает прошлое, но предсказывает (wear-out tree-sitter, combinatorial explosion flags, future ASP v0.2 risks).

### Open questions

- **Q1:** Можно ли **количественно** оценить `O` (а не качественно «+1/-1/0»)? Это требует операционализации «практической суммы активностей минус сопротивлений».
- **Q2:** Применима ли эта ретроспектива к другим проектам, не нашим? Нужны **независимые** кейсы для валидации.
- **Q3:** ADR 0005 — было ли альтернативное решение, которое сохранило бы outreach? Например, **минимальный** outreach (один пользователь раз в неделю) вместо «никакого до Gate 0→1».
- **Q4:** Если ADR 0003 (5 fixes) был бы «3 fixes» — изменилось бы общая картина? Это вопрос **порога**: где грань между разумным расширением и overcoding?
