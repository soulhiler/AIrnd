# 01. Постановка проблемы: переусложнение в AI-assisted R&D

- **Статус:** draft v0.1 (2026-05-23)
- **Связано:** [ADR 0001](../decisions/0001-track-4-scope-methodology-of-aiassisted-research-and-development.md), [Case study трека 2](02-case-study-track-02-asp.md)

## Простыми словами

Когда программу пишет человек — он медленно. Это раздражает, но создаёт **естественный тормоз**: между «я подумал» и «я написал» проходит много времени, успеваешь усомниться, успеваешь спросить совета. С AI-помощником этого тормоза нет. За одну сессию можно написать недельный объём кода. Звучит круто, но беда в том, что **проверять** этот код всё равно надо в человеческом темпе. Получается «гонка»: AI генерирует, человек не успевает отрецензировать, и куча непроверенного кода накапливается. Каждая необработанная строка — потенциальный баг, дыра в безопасности или просто лишняя сложность, которую потом придётся поддерживать.

Этот документ формализует проблему так, чтобы её можно было **измерить**, а потом **проверять**, помогают ли разные методические приёмы её решать.

## Формальная постановка

### Изучаемое явление

Группа из 1-3 человек ведёт исследовательский проект с активным использованием AI-помощника (Claude Code, Cursor agent, Cline, Goose, аналоги). Помощник не просто советует — он **сам пишет код, тесты, документацию, архитектурные решения** под управлением человека.

В таком сценарии часто наблюдается:

- **Чрезмерный объём кода** относительно цели проекта (overcoding).
- **Преждевременная архитектура** — решения принимаются без эмпирической базы.
- **Накопление непроверенного кода** — тесты есть, но они написаны с позиции «как пользоваться правильно», не «как сломать».
- **Расхождение между документацией и кодом** — ADR говорят одно, реализация — другое.
- **Низкое time-to-first-external-bug** — внешние читатели находят критические проблемы за минуты.

### Гипотеза о причине

**H1 (основная):** Производительность AI-помощника при генерации кода / документов превышает способность одного человека их валидировать в реальном времени. Этот разрыв скоростей систематически порождает overcoding.

Условно: если `V_gen` — скорость генерации (строк/час), а `V_val` — скорость валидации (строк/час), то overcoding возникает при `V_gen ≫ V_val` и отсутствии явных тормозящих механизмов.

### Что НЕ изучаем (out of scope)

- Случаи, когда AI-помощник используется только для подсказок, не для прямой генерации (Copilot autocomplete). Тут естественный тормоз сохранён — человек принимает или отвергает каждую строку.
- Большие команды (>10 человек). У них своя динамика, не наш фокус.
- Не-R&D работу (продуктовая разработка, поддержка legacy). Там цели и метрики другие.

## Метрики

Чтобы измерять эффект разных подходов, нужны **количественные индикаторы**. Кандидаты:

### Производственные

| Метрика | Что измеряет | Как измеряем |
|---|---|---|
| **LOC per session** | Скорость генерации | `git diff --shortstat` между началом и концом сессии |
| **Cumulative LOC** | Размер проекта | `cloc` или `wc -l src/**/*.ts` |
| **Files per session** | Структурная сложность | `find . -newer <session-start>` |
| **ADR per week** | Темп архитектурных решений | Подсчёт файлов в `decisions/` |

### Качественные / валидационные

| Метрика | Что измеряет | Как измеряем |
|---|---|---|
| **Time-to-first-external-bug (TFEB)** | Стабильность | Минуты/часы от публикации до первого баг-отчёта |
| **Bugs-per-1k-LOC found externally** | Плотность дефектов | `грубо отчёт audit / (LOC / 1000)` |
| **ADR-vs-code consistency rate** | Расхождение спеки и реализации | Ручной аудит: какой % ADR's имеет соответствующий код |
| **Adversarial test coverage** | Защита от атак | % файлов с тестами «как сломать» |

### Процессные

| Метрика | Что измеряет | Как измеряем |
|---|---|---|
| **Outreach round count** | Внешняя валидация | Количество завершённых раундов outreach (письмо → ответ → ответ) |
| **Sessions between gate transitions** | Темп фаз | Подсчёт по notebook entries |
| **Lit-review coverage half-life** | Зрелость поиска prior art | Среднее «возраст последнего lit-review entry для design decision» |

## Baseline (трек 2 на 2026-05-22)

| Метрика | Значение | Норма (хочется) |
|---|---|---|
| Cumulative LOC (TS only) | ~3500 | ~1000-1500 (по нашему собственному анализу из ADR 0001) |
| Files в `src/` | 21 | 8-12 |
| ADR | 10 | 4-6 |
| TFEB Round 1 | ~10 минут (Alex) | дни-недели |
| TFEB Round 2 | ~30 минут (Alex re-audit) | дни-недели |
| Bugs-per-1k-LOC (внешн.) | 7 крит/3.5k LOC ≈ 2/kLOC | <0.5/kLOC |
| ADR-vs-code inconsistency | минимум 1 явная (ADR 0010 §1) | 0 |
| Outreach rounds completed | 0 (Alex — 2 раунда reviewer-side, 0 раундов с другими) | ≥3 |
| Sessions per gate transition | 1 (Phase 0 → 1 → 2 — каждая закрыта за сессию) | 5-15 |

Baseline даёт **первичные данные** для трека 4 — это **самое ценное**, что мы из трека 2 вытащили.

## Гипотезы для проверки

**H2 (code budget):** Введение жёсткого лимита на LOC за сессию (≤500) снижает Cumulative LOC в проекте к моменту первого outreach на ≥30%, не снижая количество завершённых operations.

**H3 (one feature, one outreach):** Правило «не добавляем следующую крупную фичу до получения внешней обратной связи» увеличивает TFEB в 2-5 раз (от десятков минут до часов/дней).

**H4 (adversarial tests):** Файлы с adversarial-тестами (написанными с позиции «как сломать») имеют bugs-per-file ≤50% от файлов без adversarial-тестов.

**H5 (lit-review в параллель):** Треки, ведущие lit-review параллельно с design-решениями, пропускают меньше prior art (count of "missed prior art" surfaced through external review) по сравнению с одноразовым lit-review.

**H_null:** Никакая из перечисленных техник не даёт значимого эффекта на 95% confidence. Все «эффекты» — наблюдательный bias автора.
