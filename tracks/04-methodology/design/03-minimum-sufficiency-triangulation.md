# 03 — Минимальная достаточность: триангуляция трёх источников

## Простыми словами

Мы прочитали три классические работы из разных областей: книжку Брукса про управление программистами (1975), классическую теорию надёжности машин (советская школа, 1950-1980-е) и ТРИЗ Альтшуллера (1969-1986). Они написаны **разными людьми, в разных странах, в разное время, про разные вещи**.

Но все три пришли к **одному и тому же выводу**: **меньше деталей — лучше**. Это и называется **«минимальная достаточность»**: в системе должно быть ровно столько частей, сколько нужно для её работы. Любая лишняя часть — это:

- новый источник ошибок (теория надёжности — каждая деталь может сломаться);
- слом цельности (Брукс — много фич без общей идеи разваливают проект);
- противоречие самой цели системы (ТРИЗ — идеал = функция без компоненты, чем меньше железа, тем ближе к идеалу).

**Зачем это нам:** когда три **независимых традиции** говорят одно и то же — это очень сильный сигнал. Это не одно «мнение Брукса», а **проверенный временем принцип**. Значит, наш трек 4 (как не уйти в переусложнение) стоит на твёрдой почве. И мы можем строить дальше — переносить принцип в AI-эпоху.

## Что мы нашли

Партия B лит-обзора (3 работы) закрыта. Результат — все три источника независимо сошлись на одной идее, хотя называли её по-разному:

| Источник | Как называется принцип | Главная цитата (в нашем переводе) |
|---|---|---|
| **Брукс** (lit-review [#1](../lit-review/brooks-1975-mythical-man-month.md)) | Conceptual integrity (цельность замысла) | «Лучше система с меньшим набором функций, но единым видением, чем со многим, но рассогласованно.» |
| **Теория надёжности** (lit-review [#2](../lit-review/reliability-theory-classical-foundations.md)) | Принцип минимальной достаточности | «Каждая деталь имеет ровно столько усложнения, сколько нужно для функции. Любое сверх-усложнение = новый отказ-mode.» |
| **ТРИЗ** (lit-review [#3](../lit-review/altshuller-1986-triz.md)) | ИКР — идеальный конечный результат | «Функция выполнена, а компонента нет.» |

### Почему это триангуляция

Триангуляция в науке — это когда **независимые методы** дают одинаковый ответ. Это сильнее, чем повторение одним методом много раз. У нас:

- **Брукс** — эссеистский подход, на личном опыте больших проектов IBM.
- **Теория надёжности** — математический подход, на industrial опыте машиностроения и авиации.
- **ТРИЗ** — индуктивный анализ паттернов на 40 000 патентах.

Три **разных метода исследования**, три **разные области**, **один и тот же ответ**. Значит, ответ почти наверняка верный — это не артефакт одного метода.

## Что значит «минимальная достаточность» на нашем языке

Перевод принципа на язык AI-assisted разработки (наш контекст):

### Формальное определение

**Минимальная достаточность** = система имеет такой набор фич, что:

1. Каждая фича решает реальную (а не гипотетическую) задачу пользователя.
2. Удаление любой фичи привело бы к падению реальной (а не теоретической) метрики качества.
3. Никакие две фичи не пересекаются по функции.

Если фича не отвечает хотя бы одному из этих условий — она **избыточна**.

### Проверка (тест минимальной достаточности)

Для каждой фичи задаём 3 вопроса:

1. **Без этой фичи: что бы сломалось?** (вопрос реальности задачи)
2. **Можно ли решить ту же задачу существующим компонентом?** (вопрос пересечения)
3. **Существует ли «нулевой» вариант — функция выполняется без новой фичи вообще?** (вопрос ИКР)

Если хотя бы один из вопросов даёт ответ «фича лишняя» — мы её **не делаем**.

### Применение к треку 2 (ASP) — ретроспективно

| Операция | Без неё что было бы? | Можно ли существующим? | ИКР-вариант |
|---|---|---|---|
| `asp_readFile` | Невозможно работать с файлами | Нет | Нет |
| `asp_listFiles` | Невозможно navigate | Нет | Нет |
| `asp_searchFiles` | Невозможно искать | Можно через ls + readFile, но дорого | Нет |
| `asp_findByTag` | Невозможно искать по семантике | Можно через searchFiles + regex по тегам | Возможно, **избыточна** |
| `asp_impact` | Не виден blast radius | Можно через тесты | Возможно, **избыточна** |
| `asp_retrieve` (с эмбеддингами + LLM rerank) | Хуже релевантность поиска | Можно через searchFiles с FTS5 | **Очень вероятно избыточна** для MVP |
| `asp_applyPatch` | Невозможно править файлы | Нет | Нет |
| `asp_writeFile` | Дубль applyPatch для простых случаев | Можно через applyPatch | **Возможно избыточна** |

**Итог:** 3 из 12 операций (`findByTag`, `retrieve`, `writeFile`) — кандидаты на удаление по принципу минимальной достаточности. Это согласуется с независимой оценкой 60% overcoding из case-study трека 2 ([design/02](02-case-study-track-02-asp.md)): мы бы получили `asp-min` с ~5-7 операциями вместо 12.

## Как этот принцип уже в наших правилах

Применение триангуляции к нашим текущим правилам (CLAUDE.md правила 1-6) — каждое правило **уже** так или иначе содержит идею минимальной достаточности:

| Правило | Источник в триангуляции |
|---|---|
| **#1** Decisions per session (≤1-≤3) | Брукс — ограничение коммуникаций → ограничение архитектурных коллизий. ИКР — каждое решение должно быть **нужным**. |
| **#2** One feature, one outreach | ТРИЗ — закон неравномерности развития (узкое место = валидация, не генерация). Брукс — «omit features for unity». |
| **#3** Adversarial test для security | Теория надёжности — поиск SPF (single point of failure). Без adversarial test SPF не виден. |
| **#4** Stage gates с N валидаций | Теория надёжности — series formula: каждый gate = независимая validation, повышает общую надёжность. |
| **#5** Lit-review functions of class | Брукс — «No silver bullet»: понять existing — обязательно. ТРИЗ — paтernовый анализ как метод. |
| **#6** ADR как явный выбор человека | Брукс — conceptual integrity через одного архитектора-человека. ИКР — каждая фича должна пройти через явное «нужна или нет». |

**Это не case-by-case rationalisation.** Мы пришли к правилам **раньше** триангуляции (правила сформулированы 22 мая, триангуляция закрыта 23 мая). И каждое правило независимо рифмуется хотя бы с одним из трёх источников. Это **внутренняя consistency** — наша система правил не случайна.

## Следствия для будущих треков

### Прямые

- **(1) Каждый ADR теперь содержит ИКР-секцию** (см. updated `decisions/_template.md`). Это **формальный gate**: без явного ответа на вопрос «без этой фичи: что было бы?» — ADR не считается accepted.
- **(2) Stage gate чеклист дополняется вопросом «минимальной достаточности»**: перед закрытием фазы — пройти список фич, проверить каждую на 3 вопроса теста. Если что-то можно убрать — **убрать перед closing gate**.
- **(3) Series formula как количественный baseline**. Из lit-review #2: для N компонентов в зависимой цепочке надёжность `P ≈ p_baseline^N`. Если стандарт `p_baseline = 0.99` (1% багов на компонент), то 12 компонентов = `0.99^12 ≈ 0.886` = 11% шанс падения. Это **measurable baseline** для решения «расширять scope или нет».

### Косвенные

- **(4) S-кривая ТРИЗ как индикатор фазы трека**. Если последние 3 фичи трека решили **меньше реальных проблем**, чем первые 3 — мы на потолке S-кривой, **остановиться, не наращивать**. Применимо ретроспективно к треку 2: первые 4 операции решили ~80% use cases, последние 4 — ~20%. Сигнал был, мы его игнорировали.
- **(5) Каталог приёмов разрешения «AI overcoding»** (по аналогии с 40 приёмами ТРИЗ). Уже наметили 3:
  - **Разделение во времени** (правило #2 — между фичами обязательный outreach).
  - **Разделение в пространстве** (правило #6 — AI генерирует, человек выбирает).
  - **Разделение в отношениях** (ADR 0002 — AI = генератор, human = архитектор-валидатор).

  Это **первый паттерн** для каталога. Дальнейшие должны прийти из новых треков как эмпирические наблюдения.

## Расширение через формализм Аршинских (добавлено 2026-05-23 после получения полного текста)

После получения полного текста статьи Аршинских с коллегами (2019) — [lit-review #4](../lit-review/arshinskiy-2019-software-systematization.md) — картина прояснилась.

**Их работа НЕ заменяет наш central thesis.** Они формализуют **принцип необходимости** для **классификации существующего ПО** (top-down: как разложить программы по полкам). Наш central thesis — **минимальная достаточность** как **принцип дизайна** (bottom-up: что строить, что не строить). Это **разные** вопросы.

Однако они дают **формальный аппарат**, которым мы усиливаем нашу триангуляцию:

### Что дают Аршинские

1. **Нотация `¬A → ¬B`** — формальная запись «A необходим для B» (без A нет B).
2. **Три аспекта необходимости:**
   - `→e` экзистенциальный (без A объект B не существует).
   - `→f` функциональный (без A объект B не работает).
   - `→g` целевой (без A объект B не достигает целей).
3. **Иерархия между аспектами:** существование первично, функция вторична, цель третична.
4. **«Ценность vs полезность»** — формальное разделение: ценен = необходим (нельзя удалить); полезен = достаточен (можно использовать, но возможны альтернативы).

### Перевод нашего thesis в их язык

Наша «минимальная достаточность как принцип дизайна» в их нотации:

**Фичу стоит делать тогда и только тогда, когда:**
> `¬feature → ¬(e ∨ f ∨ g) system`

То есть: без фичи **хотя бы один аспект** системы (существование / функция / цель) **разрушается**.

Если все три аспекта останутся в порядке без фичи — фича **не нужна**, нарушает принцип минимальной достаточности.

### Триангуляция теперь имеет 4 источника

| Источник | Что даёт |
|---|---|
| **Брукс** | Conceptual integrity → omit features (эссеистский thesis). |
| **Теория надёжности** | Series formula → каждая деталь = failure mode (количественный thesis). |
| **ТРИЗ** | ИКР → функция без компоненты (методологический thesis). |
| **Аршинские** | Формальный язык: 3 аспекта + нотация (formal apparatus). |

Аршинские — **не четвёртый угол треугольника**, а **усиление инструмента** для трёх существующих углов. Они дают язык, на котором можно записать Брукса, теорию надёжности и ТРИЗ единообразно:

- Брукс «omit features for unity» = «удалять фичи, не нужные для g-аспекта (цели)».
- Теория надёжности «series formula» = «каждый компонент в `¬A → ¬B` цепочке снижает суммарную надёжность».
- ТРИЗ «ИКР» = «состояние системы, где для функции `f` нет ни одного экзистенциально-необходимого компонента» (т.е. `¬компонент → ¬f` ложно для всех компонент).

### Применение к ADR template

ИКР-секция шаблона ADR ([`_template.md`](../decisions/_template.md)) обновлена: **три вопроса** вместо одного:

1. Без фичи: разрушится ли существование системы? (e-аспект)
2. Без фичи: разрушится ли функция? (f-аспект)
3. Без фичи: разрушится ли достижение цели? (g-аспект)

Если все три ответа «нет» — фичу не делаем.

Это **более тонкий instrument**, чем наш изначальный «без фичи: что было бы?». Аршинские дают **структуру** для этого вопроса.

### Открытое расследование: AI-помощники в иерархии слоёв

У Аршинских иерархия слоёв S0 (железо) → S6 (пользователь). Но **где** в этой иерархии находятся AI-помощники (Copilot, Claude)? Гипотезы:

- **Гипотеза A:** AI-помощник = новый слой `S(meta)` **поверх** S3 (инструментальное ПО), потому что AI **генерирует код** для всех нижних слоёв.
- **Гипотеза B:** AI-помощник = «теневой пользователь» в S6, потому что он действует **от имени** пользователя.
- **Гипотеза C:** AI-помощник не помещается в их иерархию — нужна **другая ось** (cross-cutting, как security).

Это **открытый вопрос для трека 4**. Возможный ADR трека 4: «Куда помещаются AI-инструменты в иерархии Аршинских?».

## Open questions (что осталось не разрешено)

1. ~~**«Cyberleninka» статья**~~ **RESOLVED 2026-05-23**. Полный текст получен через user upload. Аршинские дают **формальный аппарат**, не **principle**. Нашу триангуляцию они **дополняют**, не **переопределяют**. Подробности — см. секцию выше.

2. **Формальная мера «избыточности»**. ИКР-тест — качественный (yes/no для каждой фичи). Аршинские тоже качественные. Хотим количественный — например, «доля операций, которые без потери функции можно убрать». Тут нужно эмпирическое исследование (через outreach к нескольким проектам).

3. **Принцип минимальной достаточности vs. дешёвая генерация AI**. В классической теории каждая деталь стоит **дорого** (станки, материалы, время сборки). Принцип «убрать лишнее» естественно вытекает из стоимости. С AI каждая фича почти **бесплатна** в производстве. Но **не** бесплатна в **поддержке + ментальной нагрузке + bug surface**. Триангуляция предсказывает, что принцип всё равно работает (поддержка дорогая) — но **эмпирически проверить надо**. Это центральная H1 для трека 4.

4. **Граница между «минимально достаточно» и «слишком мало».** ТРИЗ ИКР доходит до экстремума — функция без компоненты. Но в реальности есть нижняя граница (например, для security или UX). Нужна **методология поиска оптимума**, не только верхней границы.

5. **(новое) AI-помощники в иерархии Аршинских** — куда помещать Copilot/Claude в слоях S0-S6? Гипотезы A/B/C — см. выше. Это интересный вопрос для отдельного ADR.

6. **(новое) Английская версия Аршинских** (IWCI 2019, DOI 10.2991/iwci-19.2019.22) — стоит ли её доставать отдельно? Возможно, в международной версии есть расширения, которых нет в русской.
