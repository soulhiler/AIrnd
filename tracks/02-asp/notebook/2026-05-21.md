## Узнал

- Структура программы — 6 фаз с явными gate-критериями. Закрытие трека — нормальный исход.
- Pre-registration через git-tag достаточно на начальном этапе, OSF можно отложить.
- В Треке 2 главная дизайн-развилка — расширение MCP или отдельный протокол — решается **после** литобзора, не до.
- **LSP vs MCP — разные парадигмы:** LSP — синхронизация состояния + точечные запросы (документ ↔ модель), MCP — context bus (resources, tools, sampling). ASP лежит между: code-specific семантика (как LSP) + LLM-агент-дружелюбная архитектура (как MCP).
- **Гипотеза для ADR 0001 (требует подтверждения):** ASP — это не отдельный протокол и не «толстый MCP server», а **typed code capability поверх MCP**. Сохраняет ecosystem MCP, добавляет типизацию и composability.
- **Tree-sitter сам по себе недостаточен** — даёт AST, но не name resolution и не cross-file. Нужен Stack Graphs или аналог сверху.
- **Темп выше планового:** AI-помощь сжимает «3 ключевые работы» с недели до нескольких часов. Это переопределяет реалистичные timeline — нужно пересмотреть оценки фаз.

## Update 9 — lit-review #5 закрыт: Aider RepoMap

### Простыми словами

Изучили программу **Aider** — бесплатный AI-помощник для программистов. У них есть умный способ выбирать, какие куски кода показать AI: они используют тот же подход, что Google в поиске (алгоритм PageRank), и **обязательно следят, чтобы текст уложился в заданный размер**. Эту идею — «строгий лимит размера ответа» — точно возьмём в наш стандарт.

### Подробности

Записан [gauthier-2024-aider-repomap.md](../lit-review/gauthier-2024-aider-repomap.md) (relevance 5/5).

### Что я узнал

- **Аппроксимация:** PageRank на graph файлов (NetworkX MultiDiGraph), edges = shared symbol references, multipliers для personalization (10× для chat files, 50× — нет, наоборот, 50× для chat-file-as-source, 10× для well-named identifiers).
- **Token budget — first-class invariant.** Binary search подбирает подмножество ranked tags под `map_tokens` (default 1024) с допуском 15%. **Это, возможно, главное упущение в дизайне GitNexus и LSIF** — они возвращают всё, агент сам обрезает.
- **Tree-sitter + Pygments fallback** — pragmatic degradation: если нет references query для языка, fallback на Pygments tokenization.
- **45.1k★, Apache 2.0** — license-compatible с нашими планами; можем re-implement идею (не код).
- **Output = formatted string для LLM prompt**, не JSON. Это **враждебно к multi-client** — наша спецификация обязана возвращать structured data.
- **No degradation signals** — silent fallback. Это **наш fix #5 в чистом виде**.

### Влияние на дизайн ASP / reference impl

1. **Token budget как first-class** — кандидат на ключевой принцип ASP-спеки. ASP operation должна **никогда** не возвращать narrative output больше advertised budget.
2. **ASP capability `tokenBudget`** — server заявляет default + max + granularity.
3. **Hybrid graph: файлы (для quick ranking) + символы (для precise impact)** — обе абстракции через capability negotiation.
4. **`asp/rankRelevant({query, budget, personalization?})`** — кандидат #1 на Stage 2a operation. Прямо вдохновлена RepoMap.
5. **Multipliers как declarative knobs** в спеке (не hard-coded в коде, как у Aider).
6. **Stage 2a storage:** для альфа достаточно in-memory NetworkX-equivalent. Graph DB можно отложить до Stage 2b.

### Open question — критичный для следующего lit-review

Файловый граф (Aider) vs symbol-level typed граф (GitNexus) — это **две разные архитектурные философии**. ASP-спека должна решить: одну или обе через capability. Это **сильный кандидат на отдельный архитектурный ADR** на Фазе 1.

## Update 11 — lit-review #6 закрыт: Continue.dev

### Простыми словами

Изучили программу **Continue.dev** — третий конкурент в нашем списке после GitNexus и Aider. У них **совсем другой подход** к поиску кода: они превращают все кусочки кода в «числовые отпечатки» (embeddings) — длинные ряды чисел, которые «улавливают смысл», — и потом ищут по «похожести смысла», не по точным словам. Хранят всё в локальной базе LanceDB на компьютере пользователя. Главное, чему мы научимся: **гибридный подход** (использовать несколько способов поиска одновременно — embeddings + ключевые слова + дерево синтаксиса) и **двухэтапный отбор** (сначала 50 кандидатов, потом AI выбирает топ-10).

### Подробности

Запись: [continuedev-2026-codebase-indexing.md](../lit-review/continuedev-2026-codebase-indexing.md) (relevance 5/5).

Ключевые выводы для ASP-спеки и reference impl:

1. **Hybrid retrieval = architectural pattern.** Continue не bет на один horse — комбинирует embeddings + ripgrep + tree-sitter. ASP должна **не диктовать одну стратегию**, а advertise capabilities (`vector`, `keyword`, `graph`, `hybrid`).
2. **nRetrieve / nFinal как универсальный паттерн.** Двухстадийный funnel (50 → 10 после LLM rerank) — стандартизировать как параметры ASP операций retrieval.
3. **LanceDB как Apache-2.0 storage candidate** для нашего `asp-ref`. Альтернативы: SQLite + sqlite-vec, DuckDB + vector. Решается в будущем ADR.
4. **`.gitignore` + `.continueignore` discovery convention** — ASP должна стандартизировать (возможно `.aspignore` или продвигать cross-tool standard).
5. **transformers.js local embeddings** — proof, что embeddings работают локально, без cloud API. Снимает аргумент «embeddings = vendor lock-in».
6. **Re-ranking как opt-in capability** — Continue делает it default-on, но это дорого. ASP должна сделать **opt-in**, не default.
7. **Issue #7072 («@Codebase doesn't include relevant files»)** — empirical proof, что **pure embedding retrieval недостаточен** без structural signals. Подтверждает hybrid требование.

## Update 15 — идея 001 повышена до ADR 0004

### Простыми словами

Пользователь выбрал «продвинуть идею в стандарт». Оформил **ADR 0004** — формальное архитектурное решение, что **иерархические теги становятся обязательной частью ASP-спеки**. Статус идеи 001 теперь — **promoted-to-ADR**. Любой ASP-совместимый сервер обязан поддерживать поиск по таким тегам (или явно advertise, что не поддерживает через `tagSchema: "none"`).

### Что зафиксировано в ADR 0004

1. **Schema** — каждый ASP-символ имеет поле `tags: string[]`, где каждый тег — строка-дорожка вида `a/b/c` (slash-separated).
2. **Capability negotiation** — сервер заявляет `tagSchema: "hierarchical" | "flat" | "none"`.
3. **Операция** — `asp/findByTag({tag, hierarchical?, kind?, limit?})`. С `hierarchical: true` (default) запрос `tracks` находит и `tracks/02-asp`, и `tracks/02-asp/lit-review`.
4. **Source-agnostic** — спека не диктует, откуда сервер берёт теги (из путей / вручную / LLM / гибрид). Реализаторы свободны выбирать.
5. **Reserved namespaces** — `kind/...`, `heading/level-N`, `section/{parent}`, `lang/{language}` зарезервированы спекой для cross-tool семантики.

### Riski принятые явно

- **Early commitment** — формальное измерение precision@10 пока не сделано. Toy дал directional signal, но не статистически. **Mitigation:** формальный эксперимент в backlog (Gate 2 → 3). Если данные опровергнут гипотезу — ADR amend.
- **Spec complexity** — server implementors теперь должны реализовать tag-aware queries (если advertise hierarchical). **Mitigation:** `tagSchema: "none"` — valid escape hatch.
