## Узнал

- Структура программы — 6 фаз с явными gate-критериями. Закрытие трека — нормальный исход.
- Pre-registration через git-tag достаточно на начальном этапе, OSF можно отложить.
- В Треке 2 главная дизайн-развилка — расширение MCP или отдельный протокол — решается **после** литобзора, не до.
- **LSP vs MCP — разные парадигмы:** LSP — синхронизация состояния + точечные запросы (документ ↔ модель), MCP — context bus (resources, tools, sampling). ASP лежит между: code-specific семантика (как LSP) + LLM-агент-дружелюбная архитектура (как MCP).
- **Гипотеза для ADR 0001 (требует подтверждения):** ASP — это не отдельный протокол и не «толстый MCP server», а **typed code capability поверх MCP**. Сохраняет ecosystem MCP, добавляет типизацию и composability.
- **Tree-sitter сам по себе недостаточен** — даёт AST, но не name resolution и не cross-file. Нужен Stack Graphs или аналог сверху.
- **Темп выше планового:** AI-помощь сжимает «3 ключевые работы» с недели до нескольких часов. Это переопределяет реалистичные timeline — нужно пересмотреть оценки фаз.

## Update (тот же день, после смены приоритета)

По решению — приоритет на use cases вместо последовательного литобзора. Создан [`design/02-use-cases.md`](../design/02-use-cases.md):

- **20 use cases** в 5 категориях: Refactoring (5), Search & Navigation (5), Debugging (3), Understanding (3), Modification (4).
- **Источники:** GitHub issues (Aider #4113, #1540, Cline #4389), SWE-bench Lite, обзорная литература (Kiro, GitNexus, agentic-codebase), академические работы (SWE-Search ICLR 2025, SWE-Adept, Lita и др.).
- **Feasibility matrix** по каждому use case: MCP today / MCP + typed code capability / Отдельный протокол.
- **Подтверждение рабочей гипотезы:** ASP = typed code capability over MCP. Конкретные следствия: core primitives (findReferences, dependencies, impactAnalysis), composability через batched ops, cost-awareness через token budgets, sane defaults.

**Ключевые паттерны из анализа:**

1. Composability важна для 60% use cases (сейчас N+1 запросы).
2. Типизация важна для 70% use cases (агенты промахиваются на ad-hoc tool descriptions).
3. Semantic primitives нужны в ≥10 use cases — должны быть first-class.
4. AI-задачи (similarity, conventions, semantic merge) — 15%, требуют ML inside server.

**Прогресс Gate 0 → 1:** документально подтверждён gap; ADR 0001 может быть закрыт после ревью use cases человеком.

## Update 3 — критическая находка: GitNexus

Глубокий разбор [GitNexus](../lit-review/patwari-2026-gitnexus.md):

- **39.5k★, 4.5k forks, 288 releases, 1013 commits, последний релиз 5 дней назад** — это не proof-of-concept, это работающий продукт.
- **16 MCP tools, 2 prompts, 7 resources** — включая `impact`, `rename`, `context`, `query`, `cypher` и cross-repo операции.
- **16 языков, 12-фазный DAG-пайплайн, LadybugDB + embeddings** — серьёзная архитектура.
- **Глубокая интеграция с Claude Code** (4 skills + Pre/PostToolUse hooks), Cursor (full), Codex/Windsurf/OpenCode (MCP only).
- **License:** PolyForm Noncommercial 1.0.0 — open source но noncommercial only; коммерциализация через akonlabs.com.

**Покрытие наших use cases:** 12 из 20 GitNexus решает напрямую через tools, ещё несколько — через `cypher` escape hatch.

**Это меняет картину для ADR 0001.** Изначальная гипотеза «ASP = typed code capability over MCP» оказывается **уже реализованной de facto** через GitNexus's 16 ad-hoc tools. У нас есть несколько позиций:

- **A.** ASP = RFC, формализующий GitNexus de facto API как открытый стандарт.
- **B.** ASP = протокол capability negotiation для code-MCP-серверов.
- **C.** Закрыть трек — GitNexus покрывает большую часть лучше, чем мы сможем.
- **D.** Специализация в подобласти (например, verification-aware code intelligence — пересечение с Треком 3).

**Это архитектурное решение** уровня трека, не делегируется. Требует обсуждения с Романом перед движением дальше.

**Immediate actions before продолжения:**

1. Глубоко изучить GitNexus tool schemas (точные JSON forms).
2. Проверить, есть ли формальные RFC от GitNexus или сообщества.

### Эмпирические наблюдения (детали — в [lit-review](../lit-review/patwari-2026-gitnexus.md#hands-on-experience-dogfooding-на-нашем-репо-2026-05-21))

Что сработало:

- Markdown как первоклассный контент: 411 Section / 25 File / 10 Folder nodes на наших docs.
- Cypher на полученном графе работает, status быстрый.
- Auto-instrumentation: AGENTS.md + `<!-- gitnexus:start -->` блок в CLAUDE.md + 6 SKILL.md файлов сгенерированы автоматически.

Что не сработало:

- FTS extension не скачался (network 403 на extension.ladybugdb.com).
- `query` degraded без FTS, возвращает пустые results.
- Cypher dialect не стандартный (`label(r)` вместо `type(r)`).
- Symbol lookup строгий (нет fuzzy).

### Implications для ASP-спецификации (записаны в lit-review)

1. Markdown indexing — must-have.
2. Cypher как escape hatch — узкое место для агента.
3. Auto-instrumentation — должна быть opt-in capability.
4. Network dependencies — risk для adoption.
5. Symbol resolution — нужен fuzzy ranked search в core.
