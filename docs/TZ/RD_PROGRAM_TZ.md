# R&D-программа «AI-Native Programming Stack»
## Техническое задание для разработки с использованием Claude Code

**Версия:** 1.0
**Дата:** май 2026
**Автор постановки:** Роман
**Формат:** три параллельных исследовательских трека, каждый по классическому научному циклу

---

## Контекст и философия программы

Программа исходит из наблюдения: современный стек разработки (язык → компилятор → железо) спроектирован без учёта того, что в цепочке появилось новое звено — LLM. Каждое звено эволюционировало изолированно, и на границах теряется семантика. Цель программы — исследовать **три неосвоенных стыка** в этой цепочке и опубликовать воспроизводимые результаты.

Программа задумана как **исследовательская**, не продуктовая. Метрика успеха — публикация (arXiv → workshop → конференция) и воспроизводимый артефакт (код + датасет + бенчмарки на GitHub), а не выручка. Если в процессе появится продуктовая возможность — это бонус.

**Принципы работы:**

1. Один трек ведётся одновременно — параллелить три не получится без команды. Выбор первого трека — в конце документа.
2. Каждый трек проходит шесть фаз. Переход к следующей фазе — только после явных gate-критериев.
3. Все эксперименты регистрируются заранее (pre-registration в духе OSF), чтобы не подгонять гипотезы под результаты.
4. Negative results публикуются. Если гипотеза не подтвердилась — это тоже научный вклад.
5. Claude Code используется как имплементационный помощник, но архитектурные и научные решения принимаются человеком.

**Реалистичные timeline-оценки** для одного человека с агентом (Claude Code), при условии 20+ часов в неделю:
- Трек 2 (Agent Protocol): прототип 3–4 мес, публикуемый результат 8–12 мес.
- Трек 1 (Intent IR): прототип 4–6 мес, публикуемый результат 12–18 мес.
- Трек 3 (Verifiable Zones): прототип 6–8 мес, публикуемый результат 18–24 мес.

---

## Общая структура каждого трека

Каждый трек проходит шесть фаз:

**Фаза 0. Подготовка** — обзор литературы, проверка, что идея не сделана, формирование гипотезы.
**Фаза 1. Дизайн** — формальная постановка, выбор метрик, дизайн эксперимента.
**Фаза 2. Прототип** — минимальная реализация, проверяющая базовую техническую возможность.
**Фаза 3. Измерение** — прогон экспериментов на бенчмарках, сбор данных.
**Фаза 4. Верификация** — статистический анализ, проверка устойчивости, ablation studies.
**Фаза 5. Публикация** — препринт, артефакт, доклад.

Между фазами — **gate-критерии**: условия, при которых имеет смысл переходить дальше. Если gate не пройден — либо итерируем в текущей фазе, либо **закрываем трек** (это нормально).

# ТРЕК 1. Intent-Preserving IR между LLM и компилятором

## Краткая суть

LLM при генерации кода имеет внутреннее представление о намерении (чистота функций, независимость итераций, immutability), которое в выходной текст не попадает. Компилятор пытается восстановить это статически и часто проигрывает. Гипотеза: если LLM выдаёт **sidecar-аннотации** к коду, и компилятор использует их как верифицируемые гипотезы, можно получить значимое ускорение исполнения без потери корректности.

## Фаза 0. Подготовка (4–6 недель)

### Литературный обзор

Обязательно прочитать и законспектировать:

- **Profile-Guided Optimization** в LLVM, GCC, V8 — классический аналог, но источник подсказок другой. Понять, какие именно подсказки используются и какой выигрыш дают.
- **MLIR** документация (mlir.llvm.org) — целевая инфраструктура для аннотированных представлений. Прочитать tutorial, понять концепцию диалектов.
- **Liquid Types / Refinement Types** (Niki Vazou et al.) — близкая идея «лёгких» аннотаций.
- **Type-driven optimization in Haskell, Rust** — как `Send`/`Sync`, `pure`-функции используются для оптимизации.
- Поиск на arXiv по запросам: «LLM-guided compilation», «neural compiler hints», «LLM static analysis annotations». Цель — убедиться, что **точная** идея ещё не опубликована. Если опубликована — найти gap.
- **OpenAI Codex / DeepMind AlphaCode papers** — насколько они вообще обсуждают связь генерации с компилятором.

### Сверка с актуальным состоянием

Использовать веб-поиск в Claude Code:
- Поискать на GitHub проекты по тегам `llm-compiler`, `neural-compilation`, `mlir-llm`.
- Проверить блоги: LLVM Weekly, Modular Blog, JetBrains Research.
- Проверить, не сделал ли это уже кто-то из крупных лабораторий (Google Research, Meta AI, Microsoft Research).

### Формулировка гипотезы

**H1 (основная):** LLM-генерируемые аннотации намерения (purity, parallelizability, immutability) для функций на Python, верифицированные дешёвым статическим анализом, дают **≥30% ускорение** на горячих петлях при компиляции через Numba или Cython, по сравнению с baseline без аннотаций.

**H0 (нулевая):** ускорения нет или оно неотличимо от случайного шума.

**H2 (побочная):** доля **некорректных** аннотаций от LLM не превышает 15% — то есть гипотезы достаточно надёжны, чтобы быть полезными даже с дешёвой верификацией.

### Gate 0 → 1

- Литобзор написан (5–10 страниц), идея не дублирует существующих публикаций.
- Гипотезы сформулированы измеримо.
- Понятно, какой бенчмарк и какой компилятор будут использоваться.

## Фаза 1. Дизайн (3–4 недели)

### Выбор подмножества

Чтобы не строить компилятор с нуля:

- **Язык:** Python (огромный корпус для LLM, развитая инфраструктура JIT/AOT).
- **Компилятор-таргет:** Numba (LLVM-based JIT, хорошо документирован, относительно простое расширение).
- **Альтернатива:** Cython, mypyc — посмотреть, что технически проще расширить аннотациями.
- **Решение:** на фазе 1 сделать spike (1 неделя) с обоими, выбрать тот, где проще встроить аннотации.

### Дизайн формата sidecar-аннотаций

Минимальный набор аннотаций для MVP:

```yaml
# Пример формата
function: compute_distances
location: src/geo.py:42-58
annotations:
  - kind: pure
    confidence: 0.95
    rationale: "no global state access, no I/O, deterministic output"
  - kind: parallelizable
    scope: outer-loop
    confidence: 0.88
    rationale: "iterations independent, no cross-iteration dependencies"
  - kind: immutable-after-init
    target: lookup_table
    confidence: 0.92
```

Атрибут `confidence` — критично: позволяет компилятору взвешивать риски.

### Дизайн верификатора

Для каждого типа аннотации — дешёвый статический чекер:

- `pure`: проверить отсутствие записи в `global`, отсутствие вызовов `print`/`open`/`requests` и подобного, отсутствие изменения аргументов-объектов.
- `parallelizable`: проверить отсутствие записи в общую переменную между итерациями (data dependency analysis).
- `immutable-after-init`: проверить, что нет операторов `=`, `+=` и т. п. с этим именем после инициализации.

Чекеры намеренно делаются **простыми и быстрыми**. Если чекер не справился — аннотация отбрасывается. Это даёт безопасность по умолчанию.

### Бенчмарк

Использовать существующие наборы:
- **PyPerformance** — официальный Python-бенчмарк, реалистичные нагрузки.
- **NPB (NAS Parallel Benchmarks)** — для проверки `parallelizable`.
- Кастомный набор из 20–30 функций с известными свойствами (ground truth для валидации аннотаций).

### Метрики

- **Speedup**: время исполнения с аннотациями / время исполнения без, по каждой функции и в среднем (geometric mean).
- **Annotation accuracy**: доля аннотаций, прошедших верификатор / доля корректных по ground truth.
- **Compilation overhead**: время на верификацию аннотаций (не должно «съесть» speedup).

### Дизайн эксперимента

- 3 LLM в качестве генераторов аннотаций (Claude, GPT, локальная модель типа Qwen-Coder) — для проверки model-independence.
- 3 запуска на каждую функцию — для оценки variance.
- Ablation: speedup только от `pure`, только от `parallelizable`, и т. д. — чтобы понять вклад каждого типа.

### Gate 1 → 2

- Формат sidecar формально специфицирован (JSON Schema или Protobuf).
- Выбран компилятор и понятен путь интеграции аннотаций.
- Бенчмарк сформирован, ground truth размечен.
- Протокол эксперимента pre-registered (в OSF или просто как git commit с датой).

## Фаза 2. Прототип (8–12 недель)

### Компоненты

1. **Annotator**: пайплайн, который берёт Python-код, формирует промпт, парсит ответ LLM в sidecar-формат. Здесь Claude Code очень помогает.
2. **Verifier**: набор статических чекеров на основе `ast` модуля Python.
3. **Compiler-integration**: патч/обёртка для Numba, читающая sidecar и применяющая аннотации к LLVM IR через декораторы Numba (`@njit(nogil=True, parallel=True)` и т. п.).
4. **Bench harness**: запуск, измерение, сбор статистики.

### Принцип организации кода

- Монорепозиторий, Python 3.12+, uv для зависимостей, pytest для тестов.
- Каждый компонент — отдельный пакет с чистым API.
- CI с автоматическим прогоном бенчмарка на каждый PR (хотя бы на подмножестве).
- Все эксперименты — через `make experiment-NAME`, чтобы быть воспроизводимыми.

### Gate 2 → 3

- На 3–5 «легких» функциях (например, чистый numeric loop) получен **измеримый speedup** хотя бы 20%.
- Verifier ловит хотя бы 90% намеренно неправильных аннотаций (negative test cases).
- Полный цикл «Python код → аннотации → верификация → компиляция → исполнение» работает end-to-end без ручного вмешательства.

## Фаза 3. Измерение (6–8 недель)

### Прогон на полном бенчмарке

- ~50–100 функций.
- 3 модели × 3 запуска × N функций = несколько тысяч точек данных.
- Логирование в parquet/sqlite для воспроизводимости.

### Что измеряем

- Распределение speedup по функциям (не только среднее, но и гистограмма).
- Корреляция confidence от LLM с реальной корректностью аннотации.
- Время на верификацию vs выигрыш от оптимизации.
- Где LLM системно ошибается (анализ failure cases).

### Gate 3 → 4

- Данные собраны, исходные числа есть.
- Никаких очевидных багов в эксперименте (sanity checks пройдены: baseline воспроизводим, тривиальные случаи дают ожидаемый результат).

## Фаза 4. Верификация (4–6 недель)

### Статистический анализ

- Тест значимости (t-test или непараметрические аналоги для speedup).
- Доверительные интервалы.
- Проверка устойчивости: что если использовать только одну модель? Только Numba? Только определённые типы кода?

### Ablation studies

- Speedup при использовании только `pure` аннотаций.
- Speedup без verifier (полное доверие LLM) — для оценки риска.
- Speedup с разной температурой генерации.

### Адверсариальные тесты

- Намеренно подсунуть код, где LLM «соблазнится» поставить неправильную аннотацию (например, функция, которая выглядит чистой, но дёргает thread-local state).
- Измерить false-positive rate.

### Negative results

Если основная гипотеза не подтвердилась — **детально разобрать почему**. Это публикуемый результат: «мы попробовали, не получилось, вот точные причины».

### Gate 4 → 5

- Статистически значимые выводы по H1 и H2 (либо подтверждение, либо опровержение).
- Failure modes документированы.
- Артефакт воспроизводим: чужой человек с GitHub-клоном может повторить ключевой результат за день.

## Фаза 5. Публикация (6–8 недель)

### Артефакт

- GitHub repo с README, инструкцией воспроизведения, лицензией.
- Docker-образ для воспроизведения.
- Датасет аннотаций (если позволяют terms of service моделей).

### Препринт

- arXiv, cs.PL (Programming Languages) или cs.SE (Software Engineering).
- Структура: abstract, intro, related work, design, implementation, evaluation, threats to validity, conclusion.
- Длина: 12–20 страниц.

### Конференция-таргет

В порядке сложности:
- **Workshop:** LLM4Code (при ICSE), AIware (при FSE) — порог входа разумный для первой публикации.
- **Конференции среднего уровня:** ASE, ICPC.
- **Топ:** PLDI, OOPSLA, ICSE, POPL — нужен очень сильный результат.

### Дополнительные форматы

- Пост в Modular Blog или Cloudflare blog (если кто-то заинтересуется).
- Доклад на локальном meetup-е.
- Hacker News — пост с препринтом.

# ТРЕК 2. Agent Server Protocol (ASP)

## Краткая суть

LSP (Language Server Protocol) стандартизировал общение между редактором и компилятором, решив комбинаторную проблему N×M. Сейчас LLM-агенты (Cursor, Claude Code, Aider, Continue, Cline) общаются с кодовыми базами через ad-hoc-решения. Гипотеза: стандартизированный протокол, специально спроектированный под потребности агента (а не редактора), даст экосистеме то, что LSP дал IDE-индустрии: интероперабельность, меньше дублирования, выше качество.

Этот трек — не столько «исследование», сколько **инфраструктурный проект**. Метрика успеха другая: не статья в PLDI, а **adoption** хотя бы одним крупным агентом и публикация спецификации.

## Фаза 0. Подготовка (3–4 недели)

### Литературный и индустриальный обзор

- **LSP specification** (microsoft.github.io/language-server-protocol) — изучить досконально, понять причины дизайн-решений.
- **MCP (Model Context Protocol) от Anthropic** — спецификация, текущее состояние. Возможно, ASP логично сделать **расширением MCP**, не отдельным протоколом.
- **Tree-sitter** — стандартный парсер, основа многих современных агентов.
- **Open-source агенты:** изучить, как делают context retrieval:
  - Aider (github.com/Aider-AI/aider) — Python, прозрачная архитектура.
  - Continue (github.com/continuedev/continue) — JS/TS.
  - Cline (github.com/cline/cline) — TypeScript.
  - Codex CLI (если открыт) — TypeScript.
- **Closed-source эталоны:** Cursor, Claude Code — что можно понять из публичных постов и реверс-инжиниринга.

### Поиск существующих попыток стандартизации

Веб-поиском проверить:
- «agent code protocol»
- «MCP for code»
- «AI-native LSP»
- «code context protocol»

Если что-то уже строится — присоединиться или построить **дополнение**, а не конкурента.

### Формулировка гипотезы

В этом треке гипотеза не научная, а проектная.

**H1 (адопшн-гипотеза):** существует протокол с N абстракциями, который **строго полезнее** для агентов, чем существующие ad-hoc-решения, измеряемо по: (а) количеству вызовов для типичной задачи, (б) объёму контекста, (в) скорости.

**H2 (универсальности):** один и тот же протокол сервер может обслуживать ≥3 разных агентов без ad-hoc-кода с их стороны.

### Gate 0 → 1

- Понятно текущее положение дел: что есть в MCP, что есть в каждом из агентов, что общего, что различается.
- Сформулирован gap: чего конкретно не хватает.
- Принято решение: расширение MCP или отдельный протокол.

## Фаза 1. Дизайн (6–8 недель)

Это **самая важная фаза** трека. Дальше уже имплементация.

### Сбор требований через use cases

Собрать 15–20 типичных задач агента:
- «Добавь поле в модель и обнови все места использования».
- «Найди все вызовы deprecated-функции».
- «Объясни, почему этот тест падает».
- «Покажи примеры использования этой функции в кодовой базе».
- Каждый use case → список необходимых операций.

### Дизайн API

Ключевые абстракции, которые предлагаются как первичные кандидаты (но требуют валидации):

1. **Semantic Slice**: «дай все места использования X с контекстом ±N строк, с дедупликацией».
2. **Dependency Query**: «модули, от которых зависит X, с фильтрацией».
3. **Impact Analysis**: «что сломается, если я изменю X».
4. **Causal Error Chain**: ошибка → её причина → её причина, до корня.
5. **Test-Code Mapping**: «какие тесты покрывают этот код».
6. **Change-Aware Context**: «учитывая diff, что наиболее вероятно изменится».

Каждая абстракция должна быть:
- **Композируемой**: можно комбинировать без N+1 вызовов.
- **Cost-aware**: с указанием бюджета («≤2000 токенов в ответе»).
- **Streaming-friendly**: для больших ответов.
- **Идемпотентной**: повтор не ломает.

### Спецификация

Формат — открытая спецификация в духе RFC. Опубликовать на GitHub Pages или ReadTheDocs. Использовать JSON Schema для типов сообщений.

### Reference language

Выбрать один язык для reference implementation — рекомендую **TypeScript** (большая часть агентов на нём, легко интегрировать).

### Gate 1 → 2

- Spec v0.1 опубликована.
- Минимум 3 экспериментальных пользователя готовы попробовать (можно с собственных проектов).
- Choices в дизайне обоснованы письменно: «мы выбрали X а не Y, потому что Z».

## Фаза 2. Прототип (12–16 недель)

### Reference server

Полноценный сервер для одного языка (TypeScript или Python — выбрать тот, где сообщество агентов активнее).

Архитектура:
- Парсер: tree-sitter.
- Индексер: инкрементальный, на диске (можно через SQLite или DuckDB).
- API: JSON-RPC поверх stdio (как LSP) или HTTP/WebSocket.
- Кеширование: важно для cost-эффективности.

### Reference client

Один открытый агент, который реально использует ASP. Можно сделать форк Aider или Continue с заменой их context-retrieval на ASP.

### Demo workflow

End-to-end сценарий: «Aider-fork с ASP решает задачу X из SWE-bench за меньшее количество tool calls, чем mainline Aider». Это критически важная демонстрация.

### Gate 2 → 3

- Reference server работает, индексирует средний по размеру проект (10–100к строк).
- Reference client решает реальные задачи.
- Метрики говорят, что есть выигрыш (хотя бы на одной задаче).

## Фаза 3. Измерение (8–10 недель)

### Бенчмарк

- **SWE-bench Lite** (300 задач) — стандартный бенчмарк для агентов.
- Прогнать референсный агент с ASP и без — измерить:
  - Solve rate.
  - Среднее число tool calls на задачу.
  - Средний объём контекста.
  - Wall-clock time.

### Сравнение с альтернативами

- Тот же агент с retrieval через ripgrep + AST.
- Тот же агент с retrieval через embeddings (vector search).
- Тот же агент с ASP.

### Gate 3 → 4

- Данные собраны.
- Есть статистически значимая разница хотя бы по одной метрике.

## Фаза 4. Верификация (4–6 недель)

### Cross-agent validation

Подключить ASP-server ко второму агенту (например, Cline или Continue). Проверить, что протокол действительно language-agnostic в смысле клиента.

### Stress tests

- Большие репозитории (1М+ строк, монорепо типа Chromium-fork).
- Несколько языков в одном проекте.
- Конкурентные клиенты.

### Failure modes

- Что происходит, когда индекс устаревает?
- Что если запрашиваемый файл удалён?
- Что если запрос слишком большой?

### Gate 4 → 5

- Spec stable enough для версии 1.0.
- Reference implementation production-ready (не игрушка).
- Хотя бы один external user реально использует.

## Фаза 5. Публикация и адопшн (continuous)

### Документация

- Полная spec с примерами.
- Guides по интеграции для авторов агентов и для авторов серверов.
- Migration guide с LSP/MCP.

# ТРЕК 3. Verifiable Code Zones

## Краткая суть

Формальная верификация в индустрии не прижилась, потому что писать спецификации дорого. Гипотеза: LLM может генерировать спецификации (pre/postconditions, инварианты) такого качества, что человек только ревьюит. Это превращает экономику верификации и делает её доступной в обычной разработке. Дополнительная гипотеза: SMT-солвер может статически доказать значительную долю таких контрактов, превращая runtime-проверки в compile-time гарантии.

Это **самый исследовательский** трек, требующий теоретического бэкграунда. Зато потенциально с самым высоким impact — это направление сейчас активно атакуется лабораториями, и хороший результат публикуется в PLDI/POPL.

## Фаза 0. Подготовка (8–10 недель — больше из-за теоретической глубины)

### Литература (must read)

- **Software Foundations** (Pierce) — серия книг, особенно тома про verification.
- **Dafny tutorial и Microsoft Research papers** — лучший пример «практической» верификации.
- **Liquid Types** (Vazou, Rondon, Jhala) — refinement types, мост между типами и спецификациями.
- **Z3 / CVC5** туториалы — основные SMT-солверы.
- **Lean 4 + Mathlib** — современная proof assistant с растущей AI-интеграцией.
- **Proof-Carrying Code** (Necula 1996) — концептуальная основа.
- Свежие arXiv-работы: «LLM proof synthesis», «AI for Lean», «neural theorem proving», «LLM contract synthesis».

### Существующие проекты и их анализ

- **Dafny** (Microsoft) — спецификация для C#-подобного языка.
- **F\*** (Microsoft Research) — F#-подобный с верификацией.
- **icontract** (Python) — runtime контракты.
- **CrossHair** (Python) — символическое исполнение с Z3.
- **Daikon** (старый, но классический) — invariant discovery из исполнения.
- **LeanInk, Lean Copilot** — AI-помощники для Lean.
- **Sledgehammer (Isabelle/HOL)** — автоматизация доказательств.

### Поиск существующих LLM-подходов

- arXiv: «LLM contract synthesis», «AI specification mining», «neural invariant discovery».
- Конкретно: проверить, что делают Galois Inc., Microsoft Research, проекты вокруг Lean.

### Формулировка гипотез

**H1 (синтез):** LLM может сгенерировать корректные контракты (pre/postconditions) для функций на Python с точностью ≥70% (по metric coverage относительно ground-truth contracts от экспертов).

**H2 (статическая верификация):** ≥40% сгенерированных контрактов могут быть **статически доказаны** через SMT-солвер (для функций без сложных циклов и динамической диспетчеризации).

**H3 (полезность):** контракты находят **реальные баги** в production-коде, не пойманные обычными тестами и type-checker'ами.

### Gate 0 → 1

- Литобзор написан, gap чёткий.
- Понятно теоретическое основание (refinement types vs full verification — выбран подход).
- Есть базовое владение Z3 (можешь сам написать простые формулы и проверить выполнимость).

## Фаза 1. Дизайн (8–10 недель)

### Выбор подмножества Python

Полноценная верификация Python — задача на десятилетие. Нужно ограничиться:
- Чистые функции (без I/O, без global state).
- Числовые и stringовые операции.
- Простые структуры данных (list, dict, tuple).
- Без классов, наследования, метаклассов, eval.

### Дизайн языка контрактов

Минимальный синтаксис на базе декораторов:

```python
@require(lambda x: x > 0, "x must be positive")
@ensure(lambda result, x: result == x * x, "returns x squared")
def square(x: int) -> int:
    return x * x
```

Поддерживать:
- `@require(pred)` — precondition.
- `@ensure(pred)` — postcondition (с доступом к result и аргументам).
- `@invariant(pred)` — class invariant.
- `@variant(expr)` — для проверки терминации циклов.

### Дизайн LLM-pipeline

Промпт включает:
- Код функции.
- Тип-аннотации.
- Docstring (если есть).
- Примеры использования (если доступны).
- Несколько few-shot примеров контрактов.

Выход — JSON со списком предложенных контрактов с rationale.

### Дизайн SMT-бэкенда

- Python AST → промежуточное представление в SMT-LIB.
- Поддержка: целые числа, рациональные, булевы, массивы. Список как массив с длиной.
- Z3 как основной солвер; CVC5 как запасной.
- Timeout: 30 секунд на функцию.

### Дизайн runtime-fallback

Если SMT не справился — контракт остаётся как runtime check (через `icontract`-подобную библиотеку). Это даёт безопасность даже без статической верификации.

### Бенчмарк

- Часть стандартной библиотеки Python (выбрать чистые функции).
- HumanEval — есть ground truth по поведению.
- Собственный набор «verification challenges» с известными свойствами.
- Реальный код из open-source проектов с известными багами (для H3).

### Gate 1 → 2

- Подмножество языка формально определено.
- Синтаксис контрактов специфицирован.
- SMT-pipeline спроектирован (хотя бы на бумаге).
- Бенчмарк сформирован, ground truth размечен.

## Фаза 2. Прототип (16–24 недели)

Это объёмная фаза, требующая компиляторного/teorem-proving кода.

### Компоненты

1. **Contract DSL** — Python library с декораторами.
2. **LLM Synthesizer** — генерация контрактов через API LLM.
3. **AST-to-SMT translator** — самая сложная часть.
4. **SMT verifier** — оркестрация Z3/CVC5.
5. **Runtime checker** — fallback для недоказанных контрактов.
6. **Reporter** — структурированный вывод: что доказано, что нет, почему.

### Принципы реализации

- Корректность важнее производительности — на этом этапе.
- Каждая «упрощающая трансформация» AST→SMT должна быть **обоснована** (доказательство soundness или хотя бы аргумент).
- Тесты — отдельно на каждый компонент, плюс end-to-end.

### Gate 2 → 3

- На 5–10 функциях из стандартной библиотеки контракты успешно сгенерированы и доказаны.
- Pipeline работает end-to-end.

## Фаза 3. Измерение (8–10 недель)

### Прогон на бенчмарке

- ~100 функций.
- 3 LLM × 3 запуска × все функции.

### Метрики

- **Synthesis accuracy**: доля корректных контрактов (по ground truth).
- **Verification rate**: доля доказанных среди корректных.
- **Bug detection rate**: количество найденных багов на известных buggy codebases.
- **False positive rate**: контракты, которые «доказали», но они на самом деле слабее настоящего инварианта.
- **Time**: на синтез, на верификацию.

### Gate 3 → 4

- Данные собраны.
- Метрики посчитаны.

## Фаза 4. Верификация (8–10 недель)

### Ablation

- Только LLM без SMT.
- Только SMT без LLM (для функций, где контракты есть в docstring).
- Разные модели — насколько результат зависит от модели.
- Few-shot vs zero-shot.

### Адверсариальные тесты

- Подсунуть код с тонкими багами и смотреть, генерирует ли LLM контракт, который этот баг ловит.
- Подсунуть код, где LLM «соблазнится» написать неправильный контракт.

### Сравнение с baselines

- Mypy / Pyright — что они ловят.
- CrossHair — символическое исполнение.
- Hand-written contracts от экспертов.

### Threats to validity

- Test set bias.
- Model contamination (если LLM видел этот код на training).
- Сложность Python (тяжело гарантировать корректность трансляции AST→SMT).

### Gate 4 → 5

- Honest assessment: где работает, где не работает.
- Reproducible artifact.

## Фаза 5. Публикация (8–12 недель)

### Целевые конференции

В порядке престижа:
- **POPL, PLDI** — топ-tier для PL research, очень высокий порог.
- **OOPSLA, ICFP** — следующий уровень.
- **CAV** (Computer Aided Verification) — специализированная.
- **ASE, ICSE** — software engineering, более прикладные.
- **Workshops**: AIware, NLP4Prog.

### Артефакт

- GitHub repo с тщательной документацией.
- Lean/Coq formalization для критических теорем (если делаешь soundness claim).
- Docker воспроизводимость.
- Artifact Evaluation если конференция требует.

# Общие принципы работы программы

## Использование Claude Code

Claude Code — имплементационный партнёр, не научный руководитель.

**Что делегировать:**
- Boilerplate (тесты, CI, docs scaffolding).
- Имплементация по чёткой спецификации.
- Поиск в литературе через web search.
- Рефакторинг.
- Написание прозы черновиков (введение, related work).

**Что НЕ делегировать:**
- Архитектурные решения.
- Формулировку гипотез.
- Интерпретацию результатов.
- Решение, что публиковать.

## Управление риском

Каждый трек может провалиться. Это нормально. Признаки, что пора закрывать трек:
- Литобзор показал, что точная идея уже сделана и опубликована лучше, чем ты сможешь.
- Gate-критерии не достигаются после двух итераций фазы.
- Появилась более перспективная идея.

Закрытие трека — не поражение, а **корректное использование ограниченного ресурса (твоего времени)**.

## Pre-registration

Перед фазой 3 (Измерение) каждого трека — публично зафиксировать:
- Точные гипотезы.
- Точные метрики.
- Точную методологию.
- Stop conditions.

Можно через OSF (osf.io), можно просто через git commit с датой. Цель — защититься от p-hacking и confirmation bias.

## Публикационная стратегия

- **Negative results публикуются** — на arXiv хотя бы.
- **Препринт всегда первым шагом** — до конференции. Это устанавливает приоритет и собирает обратную связь.
- **Не гонись за топ-конференциями с первой попытки** — хорошая workshop-публикация ценнее, чем reject из PLDI.

## Open science by default

- Код — публичный с самого начала.
- Эксперименты — воспроизводимые.
- Решения — обсуждаются открыто (issues, discussions).
- Failure — тоже публикуется.
