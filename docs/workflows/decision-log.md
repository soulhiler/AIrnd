# Workflow: Decision Log (ADR)

ADR (Architecture Decision Record) — короткий документ для каждого архитектурного выбора. Цель — через год не задаваться вопросом «почему мы выбрали X, а не Y».

## Когда заводить ADR

Заводи ADR, если:
- Выбор имеет долгоиграющие последствия (формат данных, выбор языка, протокол).
- Альтернативы рассматривались всерьёз.
- Решение может быть оспорено позже.

Не заводи ADR для тривиальных вещей (имя переменной, мелкие рефакторинги).

## Формат

```bash
make adr-new TITLE="Use MCP as base protocol"
# создаст: tracks/<trk>/decisions/NNNN-use-mcp-as-base-protocol.md
```

Нумерация автоматическая, slug из TITLE.

## Структура (см. `_template.md`)

```markdown
# NNNN. Title

- **Дата:** YYYY-MM-DD
- **Статус:** proposed | accepted | superseded by NNNN | deprecated

## Context

Что происходит, какие силы действуют, что нужно решить.

## Decision

Что мы выбрали. Одно-два предложения.

## Consequences

- Что упрощается.
- Что усложняется.
- Что становится необратимым (или дорого обратимым).

## Alternatives considered

- **Alt 1:** что это, почему отклонено.
- **Alt 2:** ...
```

## Изменение решения

ADR не редактируют (кроме опечаток). Если решение пересматривается:
1. Создай новую ADR.
2. В новой укажи: `Supersedes NNNN`.
3. В старой поменяй статус на `superseded by MMMM`.

## Связь с дизайн-документом

Дизайн-документ ссылается на ADR, не дублирует их. Это позволяет дизайн-документу эволюционировать, а историю решений — оставаться неподвижной.
