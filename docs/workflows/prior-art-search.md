# Workflow: Prior Art Search

**Когда применять:** в самом начале Фазы 0 каждого трека, до глубокого литобзора foundational работ. Также при появлении любой новой идеи в любой фазе.

**Зачем:** ТЗ описывает **проблемное пространство**, не текущее состояние решений. Поле движется быстро — то, что было gap полгода назад, сегодня может быть production-продуктом с 30k★. Раннее обнаружение prior art экономит **недели** работы в неверном направлении.

**Урок-источник:** Трек 2 (ASP), 2026-05-21. Литобзор foundational работ (LSP, MCP, tree-sitter) и сбор 20 use cases — заняли несколько часов. **Глубокий разбор GitNexus** (`patwari-2026-gitnexus.md`) показал, что 12 из 20 use cases уже решены production-grade инструментом с 39.5k★. Это **переопределило позиционирование трека** ([ADR 0001](../../tracks/02-asp/decisions/0001-mcp-extension-vs-new-protocol.md)). Если бы prior art search был проведён первым шагом — направление было бы выбрано на день раньше.

## Процесс

### 1. Сформулировать «что мы собираемся построить» в 1 предложении

Без этого поиск превратится в свалку. Пример: «open-source MCP-сервер, выставляющий code intelligence operations для LLM-агентов».

### 2. Сгенерировать 5–7 поисковых запросов

Не один-два — несколько разных формулировок. Существующие решения часто называют себя иначе, чем мы.

Шаблоны:

- `"<keyword1>" "<keyword2>" github`
- `"awesome <topic>"` (списки)
- `"<topic>" alternatives 2026` (с актуальным годом)
- `"<topic>" MCP server` / `"<topic>" LSP` / `"<topic>" RFC`
- `"<topic>" open source`
- Названия близких технологий: `"code knowledge graph"`, `"AI codebase indexer"`, etc.
- Запросы на competing/critiquing: `"<existing tool>" alternative`, `"<tool>" vs X`

### 3. Прогнать через несколько источников

Не ограничиваться одним поиском:

- **GitHub:** `topic:<keyword>`, sort by stars и by recently updated.
- **Google / DuckDuckGo:** общий поиск + arXiv-фильтр.
- **arXiv:** последние 12 месяцев по теме.
- **HackerNews search** (`hn.algolia.com`) — что обсуждалось в дев-сообществе.
- **Awesome lists** на GitHub.
- **Product Hunt / Indie Hackers** — для коммерческих solutions.
- **Reddit:** r/MachineLearning, r/LocalLLaMA, r/programming, специфичные саб-реддиты.

Минимум — **3 разных источника**, чтобы не пропустить очевидное.

### 4. Для каждой находки заполнить мини-карточку

```markdown
- **Название:** ...
- **Ссылка:** ...
- **Maturity:** stars / forks / последний релиз / число contributors
- **License:** open / commercial / hybrid
- **Что покрывает:** в терминах наших use cases
- **Что НЕ покрывает:** наш потенциальный gap
- **Authors / company:** + контакты для outreach
```

### 5. Оценить процент покрытия наших целей

Если у вас уже есть use cases ([как в Треке 2](../../tracks/02-asp/design/02-use-cases.md)) — посчитать честно, сколько процентов prior art решает.

Если use cases ещё нет — оценить «80% / 50% / 20%» интуитивно, но **зафиксировать письменно** в журнале.

### 6. Применить правило решения

| Покрытие prior art | Решение |
|---|---|
| **<30%** | Gap реальный, продолжать как планировали. |
| **30–60%** | Сильное пересечение — **сузить scope** или **специализироваться** в подобласти. |
| **60–80%** | Переопределить контрибуцию: **формализация**, **интеграция**, **комплементарная функциональность**. Не «строить заново». |
| **>80%** | **Кандидат на закрытие трека** или контрибуция в существующий проект. По ТЗ это нормальный исход. |

### 7. Зафиксировать в артефакте

Создать файл `tracks/<trk>/lit-review/_prior-art-survey.md` со всеми находками. **До** того, как уйти в глубокий разбор foundational работ.

Если решение по треку меняется по результатам survey — оформить ADR.

## Поиск маркеров «уже сделано»

Сигналы, что идея реально реализована и нет смысла строить с нуля:

- ✅ ≥10k★ на GitHub.
- ✅ Релизы в последние 30 дней.
- ✅ ≥30 contributors.
- ✅ Интеграция с известными продуктами (IDE, агенты, фреймворки).
- ✅ Документация на отдельном сайте, не только в README.
- ✅ Коммерческая компания за проектом (= долгосрочная поддержка).

Сигналы, что **gap всё ещё есть, несмотря на существующие решения**:

- ⚠️ Лицензия закрытая или noncommercial (закрывает часть рынка).
- ⚠️ Lock-in к одной платформе (vendor lock-in).
- ⚠️ Закрытая разработка / закрытая спецификация (нет открытых стандартов).
- ⚠️ Узкая поддержка языков / платформ.
- ⚠️ Низкая ёмкость по нагрузке (например, in-memory only).
- ⚠️ Отсутствие formal verification / test suite.

Эти сигналы — кандидаты для **переопределения контрибуции**, а не «нет gap».

## Anti-patterns

### 1. «У нас уникальная идея» без поиска

Если убеждённость есть **до** поиска — это не сигнал об уникальности, это confirmation bias. Минимум 30 минут активного поиска перед фиксацией.

### 2. Глубокий литобзор foundational работ до prior art search

Прочитать спецификацию протокола на 200 страниц легко и приятно. Но если поверх этого протокола уже есть production-сервер с 30k★ — литобзор не приближает к решению.

**Порядок:** prior art survey → foundational lit-review (если survey не закрыл трек) → use cases → design.

### 3. Игнорирование коммерческих решений

«Они закрытые, нам не подходят» — поверхностный отказ. Часто:

- Открытое ядро + commercial layer (как GitNexus + Akon Labs).
- Бесплатный tier для исследований.
- Возможность партнёрства / контрибуции.
- Информация о компании раскрывает направление развития поля.

Минимум — прочитать README / pricing page.

### 4. Survey без фиксации в файл

«Я погуглил, ничего интересного не нашёл» — не воспроизводимо. Через месяц нельзя проверить, что именно искали и что нашли. Минимум — `_prior-art-survey.md` с запросами и находками.

## Связь с другими workflows

- **[`lit-review.md`](lit-review.md):** prior art search — **первый шаг** литобзора. Конкретные находки потом получают полную lit-review запись.
- **[`decision-log.md`](decision-log.md):** если survey меняет направление трека — оформляется ADR с обоснованием.
- **[`lab-notebook.md`](lab-notebook.md):** запись «провёл prior art survey, найдено N проектов, главное — X» — отдельный пункт в журнале.

## Чеклист на запуск нового трека

- [ ] Сформулировано «что мы строим» в 1 предложении.
- [ ] Сгенерировано ≥5 поисковых запросов.
- [ ] Прогнано через ≥3 источника.
- [ ] Каждая находка — карточка в `_prior-art-survey.md`.
- [ ] Оценено % покрытия наших целей.
- [ ] Применено правило решения.
- [ ] Если направление меняется — ADR.
- [ ] Запись в журнал.

**Без выполнения этого чеклиста deep lit-review не начинается.**
